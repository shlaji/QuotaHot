# 任务：[功能名称]

**输入**: `/specs/[###-feature-name]/` 中的设计文档

**前置条件**: plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试**: 以下示例包含测试任务。测试是可选的，仅在功能规格说明明确要求时包含。

**组织方式**: 任务按用户故事分组，以便独立实现和测试每个故事。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**: 可以并行执行（不同文件、无依赖）
- **[Story]**: 此任务所属的用户故事（例如 US1、US2、US3）
- 描述中包含准确的文件路径

## 路径约定

- **单项目**: 仓库根目录下的 `src/`、`tests/`
- **Web 应用**: `backend/src/`、`frontend/src/`
- **移动端**: `api/src/`、`ios/src/` 或 `android/src/`
- 以下路径假定采用单项目结构，请根据 plan.md 中的结构调整

## 依赖关系与执行顺序

### 阶段依赖

- **初始化（阶段 1）**: 无依赖，可立即开始
- **基础工作（阶段 2）**: 依赖初始化完成，阻塞所有用户故事
- **用户故事（阶段 3 及之后）**: 均依赖基础阶段完成
  - 之后可以并行推进用户故事（人员充足时）
  - 也可以按优先级顺序推进（P1 → P2 → P3）
- **完善（最终阶段）**: 依赖所有需要交付的用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**: 基础工作（阶段 2）完成后即可开始，不依赖其他故事
- **用户故事 2（P2）**: 基础工作（阶段 2）完成后即可开始，可以与 US1 集成，但应可独立测试
- **用户故事 3（P3）**: 基础工作（阶段 2）完成后即可开始，可以与 US1/US2 集成，但应可独立测试

### 每个用户故事内部

- 测试（如包含）必须在实现之前编写，并确认测试失败
- 先模型，后服务
- 先服务，后端点
- 先核心实现，后集成
- 当前故事完成后，再推进下一优先级的故事

### 可并行执行的工作

- 所有带 [P] 标记的初始化任务均可并行执行
- 所有带 [P] 标记的基础任务均可并行执行（在阶段 2 内）
- 基础阶段完成后，所有用户故事均可并行开始（团队能力允许时）
- 同一用户故事中所有带 [P] 标记的测试均可并行执行
- 同一故事中带 [P] 标记的模型任务可并行执行
- 不同团队成员可并行处理不同用户故事

## 实施策略

### MVP 优先（仅用户故事 1）

1. 完成阶段 1：初始化
2. 完成阶段 2：基础工作（关键阶段，阻塞所有故事）
3. 完成阶段 3：用户故事 1
4. **停止并验证**: 独立测试用户故事 1
5. 就绪后部署或演示

### 增量交付

1. 完成初始化与基础工作 → 基础就绪
2. 添加用户故事 1 → 独立测试 → 部署或演示（MVP！）
3. 添加用户故事 2 → 独立测试 → 部署或演示
4. 添加用户故事 3 → 独立测试 → 部署或演示
5. 每个故事都增加价值，同时不破坏之前的故事

### 团队并行策略

有多名开发者时：

1. 团队共同完成初始化与基础工作
2. 基础工作完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 备注

- [P] 任务表示涉及不同文件且无依赖
- [Story] 标签将任务映射到具体用户故事，便于追溯
- 每个用户故事都应可独立完成和测试
- 实现前先验证测试会失败
- 每完成一个任务或一组逻辑相关的任务后提交
- 可在任意检查点停下，独立验证故事
- 避免：含糊的任务、同一文件冲突，以及破坏独立性的跨故事依赖
