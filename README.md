# QuotaHot

主命令为 `quotahot`，独立钩子命令为 `quotahot-hook`。程序只使用新的配置和存储契约，不迁移旧数据。
Linux 安装使用 `quotahot.service`。

多账户 5 小时窗口保活工具。TypeScript 全栈：Hono 后端 + React 前端。

在你设定的**每日时段**内（默认 06:00–23:00），它会为每个 Claude / ChatGPT 账户按**各自**的限额窗口节奏，周期性发送一段自定义文本。Web 界面分三页：**账户页**展示每个账户的套餐、订阅有效期、5 小时与每周两条用量条、窗口重置倒计时，以及这台电脑此刻正在用哪个账户；**调度任务页**负责起停调度、挑选这次要跑哪些账户，并按账户列出下次/上次发送时刻；**配置页**按保活发送 / 发送时机 / 额度查询 / 本机客户端 / 网络 / API 服务分组放所有参数。实时日志在账户页和调度任务页都能看到。

账号池还能反过来用：打开 **API 服务**之后，本程序在同一个端口上多出一组 OpenAI / Anthropic 兼容的 `/v1/*` 接口，把请求转发给池子里还有额度的那个账户，每张卡片上自己决定要不要出借这个账户的额度，见 [API 服务](#api-服务把账号池变成一个转发端点)。

自动切换账户是另一个可独立构建、安装和运行的程序，见 [`hooks/README.md`](hooks/README.md)。

```
┌─ React 前端 ────────────────────────────────┐
│  账户页：动作条 + 账户卡片 × N + 实时日志      │
│         （多窗口用量条 + 套餐 + 订阅到期）     │
│  调度页：起停 + 选账户 + 下次/上次发送一览     │
│  配置页：文本 / 每日起止时刻 / 代理 / 模型      │
│         / 高级参数                           │
└──────────────┬──────────────────────────────┘
               │ REST + SSE
┌──────────────┴──────────────────────────────┐
│  Hono 服务端                                 │
│    Scheduler ── 每账户一条独立循环            │
│    Providers ── Claude 走本机 claude CLI      │
│                 Codex 直连 ChatGPT           │
│    RateLimit ── 解析上游限额头                │
│    Usage     ── 只读查询额度（不消耗窗口）     │
│    Store     ── node:sqlite 持久化            │
│    Creds     ── 自有账户目录 + 刷新/跟随客户端 │

│    Import    ── 从本机其他客户端导入账户        │
│    OAuth     ── PKCE 登录新账户                │
└─────────────────────────────────────────────┘
```

## 账户从哪来

程序有**自己的账户目录**，固定在 `~/.quotahot/accounts/`（随 `QUOTAHOT_DATA_DIR` 走）。它不直接读写别的客户端的凭证文件。

有五种方式往这个目录里放账户，都在账户页**管理账户**弹窗里：

| 方式 | 说明 |
|---|---|
| 导入 cli-proxy-api | 读 `~/.cli-proxy-api/*.json` |
| 导入本机 CLI | `~/.codex/auth.json`（Codex CLI）与 `~/.claude/.credentials.json`（Claude Code） |
| 导入 Qoder IDE | `<用户数据目录>/User/globalStorage/state.vscdb`（Linux `~/.config/Qoder`、macOS `~/Library/Application Support/Qoder`、Windows `%APPDATA%\Qoder`） |
| 上传 Token JSON | 上传单个 JSON 对象或对象数组，支持 Claude / Codex 账户及 cockpit-tools 的 Claude/Codex 导出 |
| 直接登录 | Claude / Codex 走 OAuth 授权码 + PKCE，浏览器里完成授权后把回调地址粘回来；Codex 另可改用设备码，只念一串验证码；Qoder 走设备码，点完就好 |

Token 文件一次最多上传 20 个，每个不超过 1 MiB；不支持直接上传纯文本 token。内容会拷贝到 QuotaHot 自己的账户目录，原文件不会被修改，也不会被记作客户端同步来源，之后不会再从上传文件同步。缺少 `refresh_token` 仍可导入，但不会自动刷新；再次上传相同 provider 与邮箱的账户会替换已有账户。

从 cockpit-tools 导出时可直接上传 Claude 或 Codex 的 JSON 文件：Codex 使用导出对象里的 `tokens`，Claude 使用 `claude_credentials_raw.claudeAiOauth`。Qoder 的 cockpit-tools 导出只包含账户和额度快照，不包含可迁移的登录令牌，因此不能通过 Token JSON 导入；请使用「导入 Qoder IDE」或在 QuotaHot 中重新登录 Qoder。

导入是**一次性拷贝**：原始凭证不会被改写，Codex CLI 和 Claude Code 照常可用。首次启动时如果账户目录是空的，会自动从 `~/.cli-proxy-api` 导入一次，老用户升级上来不必手动操作。

表里这些路径是**默认位置**，不是写死的。装在别处（`CODEX_HOME` 改过、凭证放在另一块盘上）就直接在「管理账户」的导入弹窗里改：每个来源那行路径本身就是输入框，就在「本机没有这个路径」这句话旁边，填完离开输入框即生效——按新位置重扫一遍，同时存进配置，重启之后不必再填。填绝对路径，留空即恢复默认位置；`~` 会展开成主目录。改一处，导入、跟随客户端、写回客户端、「本机在用」核对四处一起跟着走——只改其中一处的话，会出现「导入读 A、写回却写 B」这种谁都看不出来的错位。

### Qoder：只查额度，不参与保活

Qoder 卖的是**按订阅周期发放的 credits**，没有会自己重置的 5 小时窗口，发一条消息只是纯消耗。因此不管是导入进来的还是在这里登录的，它虽然出现在账户列表里，却**不进调度器**：不出现在调度任务页、不排下次发送、不参与批量发送，卡片上也没有「测试文本」按钮，`/send-now` 传进 Qoder 账户会直接返回「Qoder 只做额度查询，不发送保活文本」。它的额度条显示绝对数量（如 `125 / 500 credits`），加油包单列一档并标注「无重置窗口」。

Qoder 的凭证不在 JSON 文件里，而在 VS Code 式的 `state.vscdb` 里被 Electron safeStorage 加密过，本程序在导入时就地解密：Linux 走 `secret-tool` 取 keyring 密钥，macOS 走 `security find-generic-password` 读钥匙串，两者都带空密码回退；**Windows 用的是 DPAPI + AES-256-GCM，纯 Node 解不开，暂不支持**。Qoder 也没有可用的 refresh token 链路，所以从 IDE 导入的账户固定按「跟随客户端」处理，续期由 IDE 自己做，本程序每次用之前回同一个库里重读一遍。

#### Qoder 登录：设备码，不用粘贴

本机没装 Qoder、或者不想去翻 IDE 的库时，可以直接在「登录新账户」里登 Qoder。它用的是官方 IDE 那套**设备码**流程，和另外两家的授权码流程结构不同：

1. 本程序生成 `nonce` 和 PKCE 挑战，拼出 `https://qoder.com/device/selectAccounts?nonce=…&challenge=…&challenge_method=S256&redirect_uri=qoder://…` 交给用户打开；本机 IDE 缓存里读得到设备标识时一并带上。
2. 用户在网页上选好账号。授权页最后跳的是 `qoder://` 自定义协议，**本机监听接不住，也没有 code 能复制**，所以界面上不显示粘贴框。
3. 服务端每 2 秒 `GET /api/v1/deviceToken/poll?nonce=…&verifier=…` 问一次结果（未完成时上游回 404），拿到令牌后再依次取 `/api/v1/userinfo`、`/api/v3/user/status`、`/api/v2/user/plan`、`/api/v2/quota/usage` 补齐身份和额度，最后落盘。链接十分钟内有效，点「取消」会立刻停掉轮询。

其中只有 `/api/v3/user/status` 是必须成功的：它同时承担身份确认和**准入检查**——企业版的 IP 白名单、席位、应用开关都只体现在它的 `whitelistStatus` 上，登录时就挡掉，免得存进来一个到查额度时才发现用不了的账户。其余三个接口失败只是少几个展示字段。

`code_verifier` 和 `nonce` 只留在服务端内存里，不写盘也不出现在给前端的响应中。这样登进来的账户卡片上标的是**不自动续期**而不是「跟随客户端」：它没有记下可跟的原客户端，令牌失效后要么重新登录一次，要么改从 Qoder IDE 导入。点一下那枚标签会核对本机 Qoder IDE 此刻登录的账户，是同一个就把它接上，之后按跟随模式续期。

### 续期方式：自动刷新还是跟随客户端

每个账户都可以选令牌到期后怎么办，卡片右下角的按钮随时能改：

| 方式 | 行为 | 默认用在 |
|---|---|---|
| 自动刷新 | 过期前 10 分钟拿 `refresh_token` 向令牌端点换一份新的，原子写回账户目录 | 本程序登录、cli-proxy-api / Codex CLI 导入 |
| 跟随客户端 | **不做任何 OAuth 刷新**，令牌临近过期时回到原客户端的凭证文件里取它续好的那一份 | 从 Claude Code、Qoder IDE 导入的账户 |

Claude Code 导进来的账户默认跟随客户端，因为刷新会**轮换** refresh token：两个程序拿着同一份各刷各的，后刷的那次会让先前那份失效，用户下次打开 Claude Code 就得重新登录。跟随模式下本程序只用同步过来的 token 查接口，续期完全由 Claude Code 自己管，账户目录里那份只是它的一个副本。

同步是纯本地的文件读取，不发任何网络请求。客户端那边还没续期时，卡片上会写明「等客户端自己续期」并等下一轮，而不是替它去刷新。因为不需要 `refresh_token`，跟随模式的账户即使原文件里没有 refresh token 也能导入。

跟随模式同样校验 `id_token` 与 `access_token` 的账户一致性：客户端换了账号时拒绝同步，免得卡片上写着 A 实际却在查 B 的额度。

**续期方式就是卡片上那一枚标签**，上面写的是这个账户此刻用的哪一种，点它就换另一种，每个账户都点得动。Qoder 是唯一的例外：它没有可用的 refresh 端点，「自动刷新」对它并不存在，那一下只会核对本机 Qoder IDE 的登录再接上去跟随。

**两个方向都先核对身份**：读一遍本机那个客户端此刻的登录，确认它就是这个账户——Claude 比 `~/.claude/.credentials.json`（登录的是谁记在 `~/.claude.json` 的 `oauthAccount` 里，它的 access token 不是 JWT，解不出身份），Codex 比 `~/.codex/auth.json` 的 `account_id` 和邮箱，Qoder 比它 `state.vscdb` 里的 `userId`。位置按 provider 定，只有来源本身就是这些客户端时才回 `sync_path`；**cli-proxy-api 不算客户端**——它的账户目录里一个账户一个文件，拿它核对等于这个账户跟自己的副本比，永远一致。令牌一模一样就是同一份登录，直接放行；对不上就不给切，并写明那个客户端现在登录的是谁。凭证读不出、或一项身份都比不出来时同样拦下——确认不了是不是同一个账户，跟随的就可能是别人。核对通过时会把定位到的文件记进账户文件（`sync_path`/`sync_source`），跟随之后就从那里取令牌。

同一道核对在**改为自动刷新**时也做，但结论反过来用：对得上说明客户端手里那份和我们是同一份登录，本程序一刷新它就作废了，于是提醒一句「需要时用『同步账户』写回去」——只提醒，不拦。客户端已经换成别的账户时切过去反而正是要做的事：这个账户从此不再被别人的令牌顶掉。

登录有几条收尾路径，界面会自动选：

- **本地监听**。Codex 注册的回调地址正是 `http://localhost:1455/auth/callback`，所以浏览器和本程序在同一台机器上时，会在回环地址上起一个临时服务把回调接住，用户点完授权就结束了，不用复制任何东西。
- **服务端轮询**。Qoder 的设备码流程没有回调可接，由服务端自己去上游问结果，对用户来说同样是点完就结束。
- **手动粘贴**。端口被别的程序占着（多半是官方 CLI 正在登录）、或者程序跑在服务器/容器里而界面开在另一台机器上时，把浏览器最终停留的地址粘回输入框即可。

Claude 只有手动粘贴这一条：它注册的回调是 `platform.claude.com` 上的一个页面，换成 localhost 会被授权服务器直接拒掉。那个页面会把 `code#state` 显示出来，粘回来就行。

监听只绑 `127.0.0.1` 和 `::1`，并且仍然校验 `state`，不会替别人的授权收尾。只要有一个回环地址被占用就整体放弃监听退回手动——浏览器可能连的正是被占的那个，回调会送进别的进程。点**取消**会立刻把端口还回去，不必等这次授权过期。

`code_verifier` 只存在服务端内存里，10 分钟未完成即作废，不落盘。

#### Codex 设备码：既不接回调，也不用粘贴

上面那几条都要求浏览器和这个进程之间存在某种联系——要么同机以便接住回调，要么用户能把地址栏里那一长串复制回来。程序跑在远端、手边只有手机时两者都不成立。这时在 Codex 那一栏点**改用设备码**：

1. 服务端向 `POST https://auth.openai.com/api/accounts/deviceauth/usercode` 申请一组 `device_auth_id` + `user_code`，界面上只显示后者——一串好念好敲的短码。
2. 用户在**任意一台设备**上打开 `https://auth.openai.com/codex/device`，输入这串码并完成授权。
3. 服务端按上游给的 `interval` 轮询 `POST .../deviceauth/token`（没输完时回 403/404，这是常态不是错误），授权一完成就取回 `authorization_code` 和**上游代签的** `code_verifier`。
4. 拿这两样走同一个令牌端点收尾，只是 `redirect_uri` 换成设备码注册的 `https://auth.openai.com/deviceauth/callback`——本地那份 PKCE 挑战在这条路上对不上，用不得。

因此这条路不占 1455 端口、界面上没有粘贴框，验证码 15 分钟内有效。`device_auth_id` 和授权码同样只留在服务端内存里。

Codex 侧还会校验 `id_token` 与 `access_token` 里的 `chatgpt_account_id` 是否一致；不一致时**拒绝写回**这次刷新结果，以免把账户目录里的两份凭证拼成互不匹配的组合。

### 本机在用：这台电脑现在用的是哪个账户

账户目录里摆着一排账户，可你在终端里敲 `claude` 或 `codex` 时，用的只是其中一个。这件事只写在客户端自己的凭证文件里，光看邮箱猜不出来——何况 `quotahot-hook` 还会在额度撞墙时替你换一个。所以账户卡片上多了一枚**本机在用**标记，写明是哪个客户端在用它：

```
本机在用 · Claude Code    max    ⇄ 跟随客户端
```

核对的方式是反过来问：逐个打开本机客户端的凭证文件，看它现在登录的是账户目录里的哪一个。看的是这四处，和[续期方式](#续期方式自动刷新还是跟随客户端)里跟随的是同一批文件（从别处导入的账户另外带上它自己记下的 `sync_path`，改过 `CODEX_HOME` 的机器才不会被漏掉）：

| 客户端 | 读哪个文件 |
|---|---|
| Claude Code | `~/.claude/.credentials.json`（登录的是谁记在 `~/.claude.json`） |
| Codex CLI | `~/.codex/auth.json` |
| OpenCode | `~/.local/share/opencode/auth.json`（随 `XDG_DATA_HOME`） |
| Qoder IDE | 它的 `state.vscdb` |

（同样是默认位置，都在「管理账户」的导入弹窗里改。）

判据与「改为跟随客户端」那道核对**共用同一套**（`creds.identityOf`）：令牌一模一样就是同一个登录，否则比账户 ID，再比邮箱，一项都比不出来就不认。两处共用是有意的——否则会出现「跟随核对不放行、列表却标着本机在用」这种自相矛盾。cli-proxy-api 不算客户端：它是另一个程序的账户目录，一个账户一个文件，谁都没在“用”其中某一个。文件不存在的客户端整个跳过，没装 OpenCode 的机器上不会看到它。

一个账户可能同时被两个客户端用着（Codex CLI 和 OpenCode 共用一份 ChatGPT 登录），标记会把它们都列出来。客户端登录的账户没导进来时不会硬安到同一家的其他账户头上，只在日志里说一句现在登录的是谁。

**周期性核对**由后台定时任务做，周期在配置页**本机客户端**组，默认 5 分钟，设成 0 就不再核对、标记停在最后一次的结果上。客户端那边换账户的路子不止一条（你自己重新登录、hook 替你切、界面上点「同步账户」），本程序都收不到通知，只能隔一段时间自己去看一眼。整个过程只读本机文件，不发任何网络请求，也不碰任何凭证。只有**变化**才写日志，没换人的那些轮次一声不吭：

```
Claude Code 现在用的是 b@x.com（此前是 a@x.com）
```

点完「同步账户」会立刻复核一次，不必等下一个周期——刚刚改的正是这个标记的依据。

### 手动强制刷新与写回客户端配置

自动刷新模式的账户，卡片上还有两个手动入口。

**更新 token**：不等到期，立刻拿 `refresh_token` 换一份新的。它与自动续期是同一段代码，唯一的差别是跳过「离过期还早」那道判断——手动点它的场景恰恰是令牌名义上还没过期、实际却已经不好使了。刷新请求照例经过出站层，因此该账户的「请求日志」里能看到完整的一条（正文里的 `refresh_token` 是占位符），过程和结果另外写进日志面板。跟随客户端的账户看不到这个按钮：在这里换令牌会立刻作废原客户端手里那份，而这正是跟随模式要避免的事。

**同步账户**：把当前令牌写回该账户对应的客户端凭证文件，也就是导入的反向操作——在本程序里登录或刷新之后，让 Claude Code、Codex CLI、OpenCode 直接用上这份令牌。动的是用户自己的文件，所以立了三条规矩：覆盖前把原文复制成 `<文件名>.quotahot-bak`；只改令牌那几个键，其余字段（`OPENAI_API_KEY`、`scopes`、模型偏好…）逐字保留；每一处改动都逐项写进日志面板：

```
已更新 Claude Code 的配置文件 /home/u/.claude/.credentials.json，共 3 处改动（原文件已备份为 /home/u/.claude/.credentials.json.quotahot-bak）
  claudeAiOauth.accessToken: sk-ant-o…kQ2f → sk-ant-o…9Xz1
  claudeAiOauth.refreshToken: (无) → sk-ant-o…7bQa
  claudeAiOauth.expiresAt: 2026/9/5 10:00:00 → 2026/9/5 18:00:00
```

令牌只留头尾，完整凭证不会出现在日志和屏幕上。文件内容本来就和当前令牌一致时什么都不写，也不留备份，所以反复点同一个按钮不会在用户目录里堆出一串 `.quotahot-bak`。如果那个文件原先属于另一个账户，日志里会额外提醒一句被顶掉的是谁——写照写，但用户得知道自己的 CLI 换了人。Qoder 不支持写回：它的凭证在加密的 `state.vscdb` 里，只能在 IDE 里登录。

写哪些文件按 provider 定：

| 账户 | 写回目标 |
|---|---|
| Codex | `~/.codex/auth.json`（令牌在 `tokens` 下，附带 `last_refresh`）**和** `~/.local/share/opencode/auth.json`（`XDG_DATA_HOME` 生效时随之改变；令牌记在 `openai` 项下，用 OpenCode 自己的 `access` / `refresh` / `expires` / `accountId` 短字段名，不写 `id_token`）。本机这两个客户端用的是同一个 ChatGPT 账号，只更新一个，另一个照样拿着过期令牌去撞额度。从 Codex CLI 导入的账户写回它自己的来源文件，那可能不在默认位置。**OpenCode 那份只在文件已经存在时才写**：没装 OpenCode 的机器上，同步一个 Codex 账户不该凭空造出一个它的凭证库，此时目标就只剩 `~/.codex/auth.json` |
| Claude | 账户的 `sync_path`；本程序自己登录进来的账户没有来源文件，就落到 `~/.claude/.credentials.json`。不写 OpenCode——它那边的 ChatGPT 登录与本程序管的 Claude 账户没有关系 |

Codex 的两个文件各写各的、互不牵连：其中一个没权限写不进去，另一个照写，日志里逐个报结果，两个都失败才算这次同步失败。ChatGPT 桌面端（`~/.config/Codex`）不在其中：那是个 Electron/Chromium 配置目录，登录状态是一份浏览器会话，存在 `Default/Partitions/codex-browser-app` 分区里；应用二进制 `/usr/lib/chatgpt/ChatGPT` 里找不到 `auth.json`、`CODEX_HOME`、`.codex` 任何一处引用，也就是说它不读 `~/.codex/auth.json`，只能在应用里自己登录。


## 5 小时窗口从哪来

窗口时间不是推算出来的，而是直接从上游读取。Claude 与 Codex 的读法不一样，因为发送方式不一样：

| 提供方 | 来源 |
|---|---|
| Claude | 发送后回头查一次只读的 `/api/oauth/usage`，取 `five_hour.resets_at`（另有 `seven_day`） |
| Codex | `x-codex-primary-reset-after-seconds` / `-used-percent` / `-window-minutes`（`primary` 即 300 分钟窗口，`secondary` 是周窗口） |
| Codex | 兜底：SSE `response.completed` 事件中的 `rate_limits.primary.resets_in_seconds` |

Codex 是自己直连发送的，因此限额信息随手就能从响应里读到，共有三级来源：**响应头 → SSE body → 429 的 `retry-after`**。三者都空、这一发却是成功的时候，按下面 Claude 那条路同样的办法估算兜底：一次成功的保活不该因为上游没报限额就把账户停掉。解析时按前缀正则匹配，而不是硬编码完整字段名，因此上游只要改后缀，不会立刻把解析打坏。

Claude 那一发是交给 `claude` CLI 的，拿不到限额响应头，所以窗口只能回头向只读的额度接口问一次——它读到的正是刚刚那一发打开的那个窗口。最多问三次，两种问不到分开对待：**计数比发送慢一两拍**（200 但窗口是空的）过 3 秒再问；**接口自己回 429**（`rate_limit_error`，它限的是这个接口，与账户额度无关）则按 15s / 45s 往上抬，上游给了 `retry-after` 就听它的（上限 60 秒）——紧追只会把限流拖得更久。这一步也不再顺带打 `oauth/profile`：套餐名在发送路径上用不着，而它是打给同一台主机的又一次请求，正好落在同一个计数器上。

**问不到窗口时按发送时刻 + 5 小时估算，标记为 `assumed`，并在日志里提醒一句**（Claude 是三次都问不到之后，Codex 是三级来源都空之后）。 这是必须的兜底：什么都不给的话调度器会认定“未取得限额窗口重置时间”，只能按失败退避排下一拍——明明发成功了，却因为读不到额度而白等一个周期。估算值是**上界**（账户本来就在窗口里时真实重置只会更早），最多让下一拍晚一点，而下一拍会重新问一次，自己就纠正回来了。

两边都读不到重置时间时，调度器先去只读额度接口把 5 小时与周窗口都问一遍，只要还有一个没到重置时刻，这一发发不出去就是意料之中的事，等到那一刻再发即可，见「失败了，还是只是额度没到点」。确实一个未到点的窗口都没有，就按失败退避排下一拍——那时候已经没有可依据的时间，猜一个出来只会更糟，但**账户不会被停掉**，退避到点了自己还会再发一次。

## 额度查询

除了从发送响应里被动读取限额，还可以**主动查一次**，这条路径是只读的：不调用模型、不消耗额度、也不会打开 5 小时窗口。

| 提供方 | 地址 |
|---|---|
| Claude | `GET https://api.anthropic.com/api/oauth/usage` |
| Claude | `GET https://api.anthropic.com/api/oauth/profile`（套餐与组织类型） |
| Codex | `GET https://chatgpt.com/backend-api/wham/usage`（备选 `.../api/codex/usage`） |
| Codex | `GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits`（重置次数明细） |

Codex 这个地址是从 ChatGPT 桌面端自带的 `codex` 二进制里提取出来的：它的路由表把每条接口成对挂在 `/wham/…` 和 `/api/codex/…` 下，当前真正被边缘转发的是 `wham`。因此候选地址是按顺序试的，**只有“地址不对”才换下一个**——404、405，以及 chatgpt.com 边缘对未路由路径返回的 HTML 403 都算；而 401 / 429 / JSON 403 是关于账户本身的真实回答，不会继续试。

一次查询能拿到：

- **套餐**（`plus` / `pro` / …）与**订阅有效期**
- **多个窗口**：Codex 的 `primary`（300 分钟）与 `secondary`（每周 10080 分钟），Claude 的 5h / 7d 系列
- **可用重置次数**：ChatGPT 每个周期发放的“立即重置用量”额度，以及**最近一张什么时候过期**（这些额度会作废，只报总数容易让人以为它一直都在）；Claude 侧没有对应概念
- **用户 ID**

Claude 的套餐名以 `profile` 接口返回的 `organization_type`（`claude_max` / `claude_pro` / …）为准，比从用量接口里猜更可靠；认不出的新类型不会被硬凑成某个已知套餐。

另外，套餐、订阅到期、用户 ID 和登录方式（Google / Apple / 密码）也会**在本地**从凭证里的 JWT 声明直接解出来，不产生任何请求。查询失败时卡片会退回显示这份本地信息，而不是整块变空。

界面上对应账户页的**查询额度**按钮（`POST /api/usage`）。除了这个按钮，程序自己查额度只有两个来源：**发送时机**（发送之前判断该不该发、发送之后读刚打开的窗口、发送失败时分辨是不是额度没到点），以及**后台定时刷新**——周期由配置页**额度查询**组的**额度刷新（分钟）**控制，默认 10 分钟，设成 0 就只在点按钮时查。

后台刷新**只在每日时段内进行**。时段外没有账户会发送，卡片上的数字也没人在看，整夜去打上游的额度接口只会给它自己的限流计数加数——而那个计数和发送共用，凌晨白加的每一笔，都可能让天亮后第一拍的窗口查询撞上 429。时段外想看一眼，点「查询额度」照样查得动。

卡片上那个「窗口重置」显示的是**这一刻真正挡着下一发的那条窗口**，跟调度器排下一拍用的是同一条规则（见下面的三条）。手动查、后台刷、发送前后落库，三条路径记的都是同一个窗口，因此卡片上的时刻和实际要等到的时刻不会各说各话。一条未到点的窗口都问不到时（上游有时会把已经重置的窗口继续报回来），保留上一次记下的那条，而不是把一个过去的时刻写成当前窗口。

> 卡片上的百分比一律是**已用**比例，与某些第三方面板显示的“剩余”正好相反。

## 调度模型

5 小时窗口是**每账户独立**的滚动窗口，从该账户在窗口里的第一次请求开始计算。因此每个账户都运行自己的循环：

```
等到当天 06:00 → 发送 → 读出 resetAt → 等到 resetAt + buffer + jitter → 再发 → … → 到当天 23:00 停
```

实现里专门避开了两个常见坑：

1. **不使用 `setTimeout(18000_000)` 这类超长定时器。** 所有等待都基于绝对时间戳，并切成 30 秒短片重算。这样机器休眠或 NTP 校时后不会整段漂移。
2. **每次发送后立刻把 `nextDue` 写入 SQLite。** 进程被杀或机器重启后，会沿用原本节奏继续，而不是白白开启新的 5 小时窗口。接回这份节奏的前提是调度真的又跑起来了，见下面的「重启之后自己回来」。
3. **多账户的首拍也要错开。** 全新起跑的账户如果都取当下这一刻，启动那一秒就会一起打向上游，因此首拍同样摊进 `jitterSeconds`。只跑一个账户时不摊——没有“一起发”这回事，点了启动就该立刻有动静。

发送的文本很短，目标是**打开并观测**窗口，而不是消耗额度。Claude 侧由本机的 `claude` CLI 代发，见下面的「Claude 怎么发」。

下一次发送按**这一刻真正挡着它的那条窗口**来排。先把不管所有模型的窗口摘掉——上游在 5 小时和 7 天两个总窗口之外，还会另报模型专属的（`seven_day_opus`、`seven_day_sonnet`，响应头里是 `7d_opus` 这样的后缀）和计费口径的超额窗口（`seven_day_overage_included`，头里叫 `7d_oi`；那个节点上挂的是 `limit_dollars` / `used_dollars` / `remaining_dollars`，是钱，不是能不能发）。**这两类用满都不挡路**：保活只发配置里那一个模型，拿另一个模型的额度或者钱的额度去挡它，账户会白等到那个周窗口重置，好几天里每一发其实都能成功。摘完要是一条不剩，就退回没摘的那份——多等一会儿是小事，交白卷会被当成「读不出窗口」直接停掉账户。

剩下的窗口按三条规则排，没有开关可调，也不需要调：

1. **有窗口用满了**（用量 ≥ 99%），就等它们全部重置——取最晚的那个。周额度用满时，5 小时窗口再怎么早重置也没用，发出去照样被顶回来。
2. **都没用满**，就等 **5 小时窗口**关闭：它还开着的时候再发一条，也开不出新窗口，纯属白发。这时哪怕周窗口重置得更早，跟的也是 5 小时窗口。
3. **连 5 小时窗口都读不出来**，才退回最早重置的那条兜底。

**起跑那一拍也走同一套规则。** 库里没有可续的排期（全新账户、上次出错时清过、或者停得太久已经过点）时，不会见了空排期就补一发：先核对一次窗口，挑出来的那条要同时过两道，才算「不该发」。

一是**它得管得着这一发**：只有用满的窗口和 5 小时窗口才是真门槛。周额度用掉三成，丝毫不妨碍 5 小时窗口被这一发打开——凭它判定不该发，第一拍会被排到周重置，而 5 小时窗口不发就永远开不出来，于是一直缺席（上游在它没计时时可能根本不报它的 `resets_at`），改期时也没有它可以据此提前，账户就这么锁死好几天，日志里还写着一切正常。二是**它得确实在计时**：上游在窗口没开时报的是「从现在起再过一整个窗口」，那不是门槛，恰恰说明额度是满的、这一发正该发出去；窗口刚开一分钟以内读不准，就再拿上次发送时刻兜一道——还落在同一个窗口里就当它在计时。

两道都过了才照它排下一拍，因为这一发既开不出新窗口，也换不来新的重置时刻，白费一次额度还把节奏整体往后拖。此外 codex 的额度响应里带着上游自己的准入结论（`rate_limit.allowed` / `limit_reached`），它说现在不许发，那就别去撞——它比用量百分比权威，能省掉一次注定被拒的发送和随后的重试退避。取窗口的口径和改期时一致：库里那份够新就直接用，旧了才去只读额度接口问一次。

**排出来的时刻不是就此定死。** 窗口自己是会动的：周额度是滚动窗口，等着等着就会放出一部分；上游也会主动重置。所以等待期间会照最新窗口重算，变了就改期，界面上的倒计时跟着一起变。不改期时不会留日志。

但等待中的循环自己不去问上游——同一份数据后台刷新已经在按周期取了，两边各查各的只会给上游的限流计数白加一笔。改期因此只有两个由头，两个都用不着新的上游调用：**每日时段被改过**（纯本地计算，最迟一分钟跟上），以及**库里的额度数据换了一份**（后台刷新刚写完一轮、界面上点过「查询额度」，或者这个账户刚发完一拍）。后两者查完会当场叫醒等着的那几条循环，倒计时随即跟着变，不用等下一次醒来。

改期用的窗口就取库里那份——它本来就是刚写进去的那次查询的成果。另外，第 3 条那种兜底窗口**只用来提前，不用来往后拖**：上游这一刻只报得出周窗口时，多半只是 5 小时窗口已经关了，按原计划发出去、再拿响应里的窗口重排，好过放着不管干等一周。

后台刷新关掉（周期设为 0）或正处在每日时段外时，等待中的账户就没人替它发现上游悄悄放宽了额度，得等这一拍到点发出去才纠正回来；想立刻纠正，在界面上点一次「查询额度」即可。

### 失败了，还是只是额度没到点

一次发送失败可能是接口坏了，也可能只是额度还没重置。两者的处理方式完全相反——前者该重试，重试不好就退避着等下一个周期；后者只要等到那一刻——而误判的代价并不对称：把「额度没到点」当成故障，下一拍会排到退避上而不是那个重置时刻，界面上还挂着一串失败。

所以**发送失败之后会回头向只读额度接口核对一次**，Claude 和 Codex 都一样：

- **有窗口已经用满**（用量 ≥ 99%）且还没到重置时刻，就等它——它才是这一发被拒的原因。两条都满时等**晚**的那个：先重置的那条解不开另一条的限制。
- **一条窗口都没用满**时，只有上游明说了触限（429），或者这一拍本来就没拿到任何窗口，才退而求其次按上面的常规节奏排。否则判定「这不是额度问题」，重试与失败计数照常走——不然一次网络故障会被装扮成等额度，一等就是几个小时。
- **认证失败、令牌刷新不了**就不必核对了：等到额度重置也一样发不出去，直接停下来叫人。
- 除此之外的失败（上游 5xx、网络不通、重试耗尽、谁都给不出窗口）**不会停掉账户**：退避之后自己再来一拍，间隔逐次翻倍、封顶一个 5 小时窗口，也就是最多等一个周期。上游一好就能接上，而停掉要等人发现并手动重启才会恢复，那才是最不容易被发现的一种断。失败计数照常累加，界面上看得见连着失败了多少次。

按额度等待时**不计入连续失败**（已经计上的会清掉）：额度没到点是完全正常的状态，计进去的话，一个健康的账户会在界面上挂着一串「连续失败」，真出故障时反倒看不出来。日志里这一条长这样：

```
额度尚未重置（7d | 已用 100%），窗口重置 2026/9/6 22:00:00
```

### 请求身份

**每个端点都按它在官方客户端里的线上形态发**。关键不是"都装成 CLI"，而是**同一个端点在真实客户端里由哪个 HTTP 栈发出，这里就照哪个发**——Claude Code 的 OAuth 控制面走的是 axios 而不是 SDK，给它套上 `claude-cli` 的 UA 反倒成了只有我们才有的特征。

| 端点 | 线上形态 |
|---|---|
| Claude 的保活发送 | 不自己发，交给本机的 `claude` CLI —— 见「Claude 怎么发」 |
| `api.anthropic.com/v1/models` | 同一套 SDK 形态，只是 `anthropic-beta` 收成 `oauth-2025-04-20` 一项 |
| `api.anthropic.com/api/oauth/*` 与令牌端点 | **axios/1.15.2**：`accept: application/json, text/plain, */*`、`connection: close`、压缩协商里没有 zstd。CLI 的这几条请求本来就不经过 SDK |
| `chatgpt.com/backend-api/codex/responses`、`/codex/models` | Codex CLI：`originator: codex-tui`、版本化 UA、`version` 头；对话那条另加 `openai-beta: responses=experimental` 和每次新的 `session_id` |
| `chatgpt.com/backend-api/wham/*`、accounts/check、subscriptions | Codex 桌面端的浏览器身份：Chrome UA + `Referer: https://chatgpt.com/` + `sec-fetch-*` |

三套身份声称的是**同一台机器**（Apple Silicon 的 macOS + iTerm2）。同一个账户上 Claude 报 MacOS/arm64、Codex 报 Linux/x86_64，本身就是个破绽，所以设备画像是共用的一组常量。Codex 的版本号同时出现在 UA、`version` 头和模型目录的 `client_version` 查询串里，三处必须一致。

令牌刷新也各按各家的形态：Claude 的端点收 JSON（axios 发的），OpenAI 的只收表单编码并带 `scope`。

Claude 的保活发送曾经也是自己拼 `/v1/messages`——请求头、`anthropic-beta` 顺序、`system` 分块、`metadata.user_id` 全部照着真实 CLI 复刻。**这条路已经走不通了**：复刻得再像也是在追一个会变的目标，上游不再受理这样的请求。现在改成直接调用本机的 `claude`，那套请求体与 `/v1/messages` 请求头的构造代码已随之删除（`server/claudecode.ts` 整个不再存在）；`headers.ts` 里剩下的 SDK 形态只服务 `/v1/models`。

出站统一走 undici 的低层 `request` 而不是 `fetch`。`fetch` 遵循浏览器语义，会强行补上 `sec-fetch-mode: cors`、缺省的 `accept-language` 之类的头——真实 CLI 绝不会发这些，而上游正是按这套指纹认调用方的。代价是要自己按 `content-encoding` 解压（gzip / deflate / br / zstd）。

出错时会把 `x-request-id` / `cf-ray` 和响应体里的 detail code 一并附在错误信息后面，便于对着上游侧的日志排查。

**凡是代表某个账户发给上游的请求都会记日志**，不只是保活发送：额度查询、profile、模型目录、令牌刷新都在内。记账做在出站的统一入口里，而不是各个调用点各写一遍，所以“全都有日志”是结构上成立的。记下的是方法、地址、全部请求头、请求体，**以及上游原样返回的响应体**；账户卡片上的**请求日志**按钮可以逐条翻看，并一键复制成等价的 curl。上游拒绝时问题基本都出在身份头上，而原因写在响应体里，光看状态码两边都看不出来。

响应体是**边流边攒**的：调用方照常读流，出站层在管道上挂一层顺手留一份，流结束时补写回同一行日志。这样流式请求也留得下痕——保活发送读到 `response.completed` 就掐断连接，完整正文根本不存在，能留下的就是已经读到的那一截。单条上限 64 KB，超出的部分截断并注明。响应体里的凭证同样不入库：我们发出去的那份按值抹成占位符，上游**新签发**的那份（令牌端点的 `access_token` / `refresh_token` / `id_token`）按字段名抹掉——否则请求侧特意避免的长期凭证会从响应侧漏回库里。

**Claude 走本机 CLI 的那一发同样在这张表里。** 它没有 HTTP 报文可记，但决定它去向的东西一样不少，于是各处按对应物存：**环境变量**记在请求头的位置（用的哪个令牌、哪个 `CLAUDE_CONFIG_DIR`、走不走代理，一眼可查）、**完整命令行**记在请求体的位置、**CLI 的 stdout 与 stderr** 记在响应体的位置——失败原因经常只写在 stderr 里，只留 stdout 就会出现“什么都看得到，唯独看不到它为什么不行”。地址写成 `cli://<可执行文件>`，界面据此认出这是本机执行而不是一次请求：状态一栏显示的是折算前的含义（发送成功 / 已触限 / 认证失败 / 未执行），复制出来的也不是 curl 而是一条可直接重跑的命令，`env -i` 打头——发送时子进程的环境是白名单重建的，换一套环境问出来的结果不算数。

令牌本身不入库：落库前按**值**匹配替换成占位符（因此令牌刷新请求体里的 `refresh_token` 同样会被抹掉，不管它出现在 URL、请求头还是请求体）。

**界面上显示的一直是占位符，只有“复制”出来的那份带真令牌。** 日志是拿来看、拿来截图问人的，令牌不该跟着出现在画面里；而复制出来的东西要能直接重发，所以那一份必须是真的。接口把日志行原样返回（占位符不动），账户当前的令牌单独放在 `secrets` 里，前端只在点复制那一下才用它把占位符换回去——真令牌从不进入 DOM。给之前服务端会 `ensureFresh` 一次，所以哪怕翻的是三天前那条请求，复制出来的 curl 用的也是此刻有效的令牌，粘进终端就能重发。复制出来的东西等同于账户凭证，别贴到公开的地方。每账户保留最近 200 条。

### Claude 怎么发

Claude 侧的保活文本**不由本程序自己发**，而是起一个子进程调用本机装好的官方 `claude`：

```
claude --print --output-format json --model <模型> --safe-mode --no-session-persistence --strict-mcp-config -- <文本>
```

原因很直接：OAuth 令牌只在 Claude Code 身份下签发，上游是按整套“请求头 + 请求体”判断调用方是不是真的 CLI 的，自己复刻出来的请求已经不被受理。真正的 CLI 就装在这台机器上，让它自己去发是唯一不会被判错的形态。

要把这件事做对，有几处不能省（都在 `server/claudecli.ts`）：

- **身份隔离**。CLI 默认读 `~/.claude` 下的登录状态；照原样调用的话，所有账户会一起用用户自己的身份去发。因此每个账户单独指一个 `CLAUDE_CONFIG_DIR`（`~/.quotahot/claude-cli/<账户>`），令牌只通过 `CLAUDE_CODE_OAUTH_TOKEN` 递进去，工作目录也设在那个空目录里，CLI 读不到任何项目上下文。
- **环境净化**。父进程里只要有 `ANTHROPIC_API_KEY` 或 `ANTHROPIC_BASE_URL`，CLI 就会优先用它们——那一发既不属于这个账户，甚至可能根本没打到官方端点。所以子进程的环境变量是**白名单重建**的，不是继承下来再删几个。代理不共享本进程的 dispatcher，另外通过 `HTTPS_PROXY` / `NO_PROXY` 告诉它。
- **版本适配**。`--safe-mode`、`--no-session-persistence`、`--strict-mcp-config` 这几个开关在版本之间增删过，传一个 CLI 不认识的参数会让整次发送直接失败。因此启动后先读一次 `claude --help`，只传它认的那几个；缺了也能发，只是运行环境没那么干净。
- **超时**。CLI 卡住会把该账户的整条循环一起卡住，所以有硬上限（3 分钟）：先 SIGTERM，5 秒后 SIGKILL，并且不等 `close` 事件——CLI 可能把 stdout 交给了自己的子进程，那样 `close` 永远不会来。

CLI 对认证失败、触限这类问题只给一个非零退出码和一段人话，没有状态码，所以按输出内容折算：`usage limit reached`、`You've hit your weekly limit` 一类归 429（照常按窗口排下一拍），`Failed to authenticate` / 403 / 401 一类归 401（停掉该账户，等用户去看凭证），其余按可重试处理。

**触限的措辞要认宽一点。** 认不出来的代价不是少记一条日志，而是这一发被当成接口故障：重试几轮全白费，下一拍还按失败退避排，额度明明已经重置也没人去发。真实事故里那句话是 `You've hit your weekly limit · resets 10pm (Asia/Singapore)`——既没有 `usage limit reached`，也没有任何状态码。

那句话尾巴上的重置时刻会一并解析出来（`resets 10pm (Asia/Singapore)`、`resets at 11:30pm`、`resets in 42 minutes` 都认，括号里是 CLI 自带的 IANA 时区名，缺省按本机时区解释；只给钟点没给日期，所以取该时区里下一次走到这个钟点的那一刻）。它排在额度接口之后、5 小时估算之前：接口能说话就听接口的，接口不肯说时这句原话也比估算强——撞的是周额度时，「发送时刻 + 5 小时」会差出好几天。窗口来源标成 `cli-message`，界面上一眼能看出这条是从错误文案里读来的。

每一发都会在**请求日志**里留一条（环境变量、命令行、CLI 输出、耗时、折算后的结果），所以“交给 CLI 去发”并不等于这一段变成黑箱——出问题时该看的东西和 Codex 那条路一样齐。

调用的就是 PATH 里的 `claude`。Codex 侧不受影响，仍然直连 `/backend-api/codex/responses`。

## API 服务：把账号池变成一个转发端点

保活解决的是「账户别闲着」，这一节解决的是另一半：**这些账户的额度，怎么让你手边的编码客户端直接用上**。打开之后，本程序在同一个端口上多出一组 `/v1/*` 接口，同时说 **Anthropic Messages** 和 **OpenAI Chat Completions** 两种方言；收到请求就从账号池里挑一个还有额度的账户，用它的凭证发给真正的上游，再把响应按客户端要的方言翻回去。

**默认是关的**，而且必须由你自己在配置页按一下。装了这个程序的人未必想在本机开一个能花掉全部额度的端点——这件事不该由默认值替谁决定。

### 开起来

1. 配置页最后一组 **API 服务** → 勾上**开启 API 服务**。旁边直接写着接入地址，形如 `http://127.0.0.1:8686/v1`，不必自己拼。
2. 同一组里填 **API key**（点「生成一个」会追加一串随机 key），多个用逗号分隔。**留空也能用，但只接受来自本机回环地址的请求**——一个没有 key 又对外监听的转发端点，等于把账号池里的全部额度公开出去。
3. 保存。
4. 回账户页，在**想出借额度的那几张卡片**上打开 **API 服务** 开关。这一步没有批量按钮，也没有默认打开：额度是你的，每一个账户都得你自己点。

四步缺一不可：服务开着但一个账户都没打开，请求会收到 503 并附一句「账号池里没有可用于转发的账户」，而不是悄悄挑一个账户替你花掉。

### 客户端怎么接

| 客户端 | 怎么指过来 |
|---|---|
| Claude Code | `ANTHROPIC_BASE_URL=http://127.0.0.1:8686` + `ANTHROPIC_API_KEY=<你设的 key>` |
| Codex CLI / 任何 OpenAI SDK | base URL 填 `http://127.0.0.1:8686/v1`，api key 填同一个 |
| curl | `curl -H 'x-api-key: <key>' -H 'content-type: application/json' http://127.0.0.1:8686/v1/messages -d '{"model":"claude-sonnet-5","max_tokens":1024,"messages":[{"role":"user","content":"hi"}]}'` |

两种 key 头都认：Anthropic 客户端发 `x-api-key`，OpenAI 客户端发 `Authorization: Bearer`，比较用的是定长比较，不会因为耗时泄露 key 的前缀。

`/v1/*` 这一族**挂在 Web 的 Basic Auth 之前**，自己校验 key。原因很实际：让 Claude Code 去应付一次浏览器式的 Basic Auth 挑战是不现实的。所以 `QUOTAHOT_AUTH_PASSWORD` 管的是界面和 `/api/*`，管不着 `/v1/*`；反过来，网关的 key 也进不了界面。两把钥匙各开各的门。

四个端点：

| 端点 | 说明 |
|---|---|
| `POST /v1/messages` | Anthropic Messages，流式与非流式都支持 |
| `POST /v1/chat/completions` | OpenAI Chat Completions，含 `tool_calls`、`reasoning_content` |
| `GET /v1/models` | 列出当前账户池可用的模型；需要带 API key |
| `POST /v1/messages/count_tokens` | 按字符折算的**估算值**。两家上游都没有只读计数接口，真要问就得发一次真请求；拿它判断「要不要压缩上下文」够用，当账单用则不行 |

### 里面是怎么走的

**Anthropic Messages 格式是内部的中间表示。** 它是两种方言里信息最全的那个：thinking 块、流式吐出来的 tool_use JSON、按块结构化的 system，OpenAI 那套里都没有对应物。以它为中心，进出各写两个转换器就够了；反过来以 OpenAI 格式为中心，或者不设中心直接两两互转，要么丢信息，要么写成一张四格的转换矩阵。

**所有出站都是流式的。** 客户端要非流式时，在本地把事件流收完再拼成一个完整响应（`collect()`）。这样上游只有一条代码路径，两种上游的差异也只体现在各自的转换器里。

- **Claude** → `api.anthropic.com/v1/messages`。OAuth 令牌是签给 Claude Code 的，上游按整套请求头加请求体判断调用方是不是真的 CLI，所以转发时会补上 `anthropic-beta: oauth-2025-04-20,claude-code-20250219`，并把 Claude Code 的身份句**插到**你的 system 前面——是插到前面而不是替换，客户端自己的提示词一个字都不丢。
- **Codex** → `chatgpt.com/backend-api/codex/responses`。那是 Responses API，只收流式、`store:false`，于是多一层 Responses ↔ Messages 的事件翻译（item 扁平化、`function_call` 的参数拼接、reasoning 分档）。

  这个端点只认 Codex CLI 用得上的那几个字段：`temperature`、`top_p`、`max_tokens` 带上去会被上游用 400 `Unsupported parameter` 整条顶回来，所以**转发时一律丢掉**。你在客户端里调这三个，走 Codex 账户时不会生效——丢掉还能出结果，带上去就是请求失败。走 Claude 账户不受影响。

- **Qoder** → Qoder 的推理 SSE 接口 `/algo/api/v2/service/pro/sse/agent_chat_generation`。Qoder 不使用导入账户里的登录 OAuth token，而是使用账户卡片上单独设置的 **Qoder PAT**。每次请求会根据账户的 `machineId`、用户身份和客户端元数据，通过内置的 WASM signer 生成 Qoder 原生签名，再把请求转成 Qoder 自己的 `chat_context`、`business`、`model_config` 等格式；上游返回的加密 SSE 分片再由 signer 解密并转换回 Anthropic/OpenAI 响应。

Qoder 转发会把客户端传入的 `model` 字符串原样传给 Qoder，包括前缀、大小写和后缀，不再按 `opus` / `sonnet` / `haiku` 识别或改写成内置档位。客户端应传入 Qoder 上游实际支持的模型标识，例如：

  ```json
  {"model":"qoder/efficient","messages":[{"role":"user","content":"hi"}],"stream":false}
  ```

  查询模型列表时使用网关接口：

  ```bash
  curl -sS \
    -H "Authorization: Bearer <你的API_KEY>" \
    http://127.0.0.1:8686/v1/models | jq
  ```

需要注意，`/v1/models` 的动态目录目前主要覆盖 Claude/Codex；Qoder 请求的模型标识由客户端自行提供并透传，服务端不提供模型识别或默认档位回退。是否进入 Qoder 仍由 provider 路由规则和跨家转发设置决定。

出站统一走 `server/http.ts`，因此**转发的每一条请求和保活、额度查询出现在同一份请求日志里**，排障时不必分两处看，令牌也照样按值抹成占位符。

### 派谁去

配置页那一组里能调的就是这几件事：

- **派活顺序**：`fill-first` 让优先级高的一直用到耗尽再换下一个（额度有过期的话这样更划算），`round-robin` 让同优先级的轮流来（额度摊平）。两种都是**优先级压过顺序**：优先级高的那个哪怕刚用过也排前面。
- **留给自己的额度**：已用比例超过这个数就不再派活。默认 100，即用到上游说没了为止；调成 80 就意味着**留 20% 给你自己的客户端**，别让后台转发把你正在写的那个功能卡在限额上。没查过额度的账户按「能接活」处理——你没点过「查询额度」，不该让一个好账户被排除在外。
- **换账户重试次数**、**连续失败几次进冷却**、**冷却时长**。
- **跨家转发**：请求的模型属于 A 家、池子里却只有 B 家账户时，允不允许转换协议后发给 B。**默认不允许**——模型能力和计费都不一样，静悄悄换一家比直接报错更难排查。

有两处判断值得单独说：

**重试换的是账户，不是把同一个再试一遍。** 客户端自己就会对网络抖动重试，我们能做而它做不到的事只有「换一份还有额度的凭证」。并且重试只发生在**流开始之前**：上游一旦回了 200 并开始吐字，客户端已经收到半句话了，这时候换账户只会让它看到两段拼不起来的回答。所以流中断一律如实往下传，不记进那个账户的失败预算。

**限流和上游抖动不记在账户头上。** 401 / 402 / 403 是这份凭证的问题，记；429 / 5xx 换个账户照样撞，不该消耗这个账户的失败预算——否则一次上游故障会把整池账户集体推进冷却，故障过去之后还得干等冷却结束。失败次数仍然照记，卡片上看得到。

### 卡片上管额度

每张支持转发的卡片上多一块：

- **开关**决定这个账户参不参与；关着的时候整块折叠成一行，好让长列表里真正在转发的那几个跳出来。
- **状态**：未参与 / 待命 / 转发中 / 冷却中 / 额度用尽 / 不可用。它和上面那条保活状态**各说各的**——一个账户完全可能「保活已停止」却正在替 API 服务干活。
- **优先级**用 −/+ 调，越大越先被派活。
- **统计**：转发了多少次、失败几次、累计 token、最近一次派活的时刻。
- 在冷却里时给一条**立刻归队**：用户按下它就是明确表达了「再试一次」，冷却和失败计数一起清掉。

设置和统计**各走各的**：改开关不会把统计清掉。它们也不写进账户的 JSON 文件——那份文件会被 `saveAccount` 按固定字段重写，加进去的东西下一次刷新令牌就没了。转发的设置和统计存在状态库的 `gateway_account` 表里。

### Qoder 账户的特殊要求

Qoder 不参与保活调度，但可以参与 API 转发。要让 Qoder 账户进入转发池，必须同时满足：账户未禁用、账户卡片上的 **API 服务** 已打开、账户卡片上已经设置 **Qoder PAT**，并且账户没有处于冷却或额度耗尽状态。Qoder 的登录 token 与转发 PAT 是两套相互独立的凭证；只打开 API 服务但没有 PAT 时，卡片状态会显示为「不可用」，不会被派活。

### 几句实话

- 这个端点花的是你账号池里的真额度，没有任何配额兜底。**对外监听时务必设 key**，并且和界面一样，必须在前面挡一层 HTTPS 反向代理或走可信隧道。
- 用 OAuth 令牌驱动第三方客户端，在两家服务条款下的位置和保活自动化一样含糊，账号存在风险，请自行权衡。
- 开关状态会写进启动日志：`API 服务: 开 · http://127.0.0.1:8686 · 需要 API key`。没设 key 时那一段会写成「未设 key（仅本机可用）」，免得你以为自己已经保护好了。

## 运行方式

需要 Node 24 或更高：状态持久化用的是内置 `node:sqlite`，它在 Node 24 起才无需实验标志（Node 22.5–23.x 要加 `--experimental-sqlite`）。

```bash
npm install

# 开发：前端 vite(5173) + 后端 hono(8686)，API 自动反代
npm run dev

# 生产：构建前端与服务端，再由 Hono 一并托管（认证可选）
npm start                 # http://localhost:8686
PORT=9000 npm start       # 使用其他端口

# 查看应用版本（不会启动 Web 服务）
quotahot version

# 可选：启用 Web Basic Auth；未设置时默认不验证用户和密码
QUOTAHOT_AUTH_USERNAME=alice QUOTAHOT_AUTH_PASSWORD='change-me' npm start
```

Web 页面顶栏会显示当前运行服务的版本号。

配置、状态数据库和账户默认放在 `~/.quotahot/`，可通过 `QUOTAHOT_DATA_DIR` 覆盖。放在主目录而不是当前目录，是为了从任何路径启动都读到同一份数据——换个终端、或者用 systemd 拉起，都不会各自建一份配置。

### Web 访问认证

服务默认只监听 `127.0.0.1`，并默认**不启用**用户名密码认证；页面、REST API 和 SSE 会保留安全响应头及跨站请求保护。需要 Basic Auth 时，同时设置 `QUOTAHOT_AUTH_PASSWORD` 和可选的 `QUOTAHOT_AUTH_USERNAME`：用户名未设置时使用 **`quotahot`**，密码不会写进启动日志，重启生效。只设置用户名而未设置密码会阻止服务启动，避免误以为服务已受保护。

远程访问优先使用 SSH 端口转发。确需监听其他地址时设置 `QUOTAHOT_HOST`，例如 `QUOTAHOT_HOST=0.0.0.0`；认证关闭时不要直接暴露到不可信网络，认证开启时也必须在前面部署 HTTPS 反向代理或通过可信加密隧道访问，Basic 认证本身不加密传输。反向代理须保留原始 `Host`，跨站请求会被拒绝。开发模式启用认证后，浏览器会在访问页面或 `/api/state` 时弹出原生认证提示。

**Basic Auth 管不着 `/v1/*`。** 那一族是给编码客户端用的，走自己那把 key（见 [API 服务](#api-服务把账号池变成一个转发端点)）——让 Claude Code 去应付一次浏览器式的认证挑战是不现实的。所以开了 Web 认证并不等于转发端点也被保护了：没设网关 key 时它只接受本机请求，要从别的机器接就必须先设一个。

令牌刷新现在按账户合并同进程请求，并以 `<账户文件>.refresh-lock.db` 的独立 SQLite 事务锁协调不同进程（不写服务端的 `state.db`）；不会仅因请求耗时长就抢锁。进程退出或被强杀时，操作系统会释放锁，无需手动删除锁文件。

### 界面使用步骤

1. 填写**发送文本**、**开始时间**、**结束时间**，然后保存配置。起止时间是**每天重复的时刻**（`HH:MM`），不含日期；两者相同表示全天。跨零点也可以，例如 22:00–02:00。
2. 点击**查询额度**。它只读取上游的额度计数，不会消耗额度，可以随时点。
3. 切到**调度任务**页点**启动定时任务**。想只给其中几个账户保活，就先在表格里勾上它们，按钮会写明这次纳入几个（一个都不勾即全部）；纳入哪些账户在启动那一刻定死，之后再改勾选不影响已经在跑的这一批。启动后账户卡片实时显示套餐、各窗口已用百分比与重置倒计时、订阅有效期以及 token 剩余有效期，下次/上次发送时刻则在调度任务页按账户列出。
4. 卡片上的**测试文本**会用当前的发送文本和模型真发一次，不会打乱调度节奏（**注意它会打开 5 小时窗口**）；旁边的**查看额度**只查这一个账户，是只读的；日志图标打开这个账户的请求日志。
5. 需要时用卡片上的**更新 token**换一份新令牌，或用**同步账户**把它写回 Claude Code / Codex CLI；改了哪些内容会逐项记进下方日志面板。
6. 每张卡片左上角的勾选框决定顶部**测试文本**和**查询额度**这两个按钮的作用范围：一个都不勾就是全部账户，勾了就只作用于勾中的那几个。批量测试和卡片上的**测试文本**是同一条路径，只是逐个账户串行执行，因此**每个被选中的账户都会各打开一个 5 小时窗口**，点下去前会先确认一次。

运行中修改配置只会影响下一拍，不会打断已经在等待的这一轮。

调度里的账户名单同样每一拍核对一次：**删掉账户、禁用它、或者把它加进 `exclude`（以及从 `include` 里拿掉），它都会在下一拍到点时退出调度**，日志里留一句「账户已删除，退出本次调度」。不核对的话，那条循环会攥着启动那一刻读进来的令牌一直发下去，而账户早就从界面上消失了（账户列表是按当前配置过滤的），没有任何地方看得出它还在打上游。想立刻生效就点一次停止再启动——每一拍最长是一个 5 小时窗口。

## 打包分发到其他机器

`npm run build` 把前端交给 vite 构建，再由 esbuild 把服务端连同前端一起打成单文件——界面的 HTML、JS、CSS 都内嵌在里面，运行时从内存发出去。因此产物是**一个文件**：不需要 `node_modules`，不需要 `tsx`，也不必随身带一个 assets 目录，从哪个目录启动都行。

构建出来的 `dist/quotahot` 带 shebang、置了可执行位，也没有扩展名——拷进 PATH 上任何一个 bin 目录就是一条命令。旁边那个只写了 `{"type":"commonjs"}` 的 `dist/package.json` 是给 `npm i -g` 用的：没有扩展名的文件按哪种格式解析，取决于往上找到的第一个 package.json，而本项目那份写着 `"type": "module"`，不钉死就会被当成 ESM 而崩在第一行 `require` 上。单拷可执行文件出去则不需要它，bin 目录里通常一个 package.json 都找不到，那默认就是 CommonJS。

```bash
npm run build
./scripts/install.sh                 # 安装到 ~/.quotahot/bin，并启动 systemd 用户服务
./scripts/install.sh --port 9000     # 安装时指定端口
```

安装脚本只支持 Linux，目标机需要 Node 24。它会按实际的用户目录和 `node` 路径生成
`~/.config/systemd/user/quotahot.service`，不需要 `sudo`；升级时直接覆盖旧的可执行文件和
服务单元，不留 `.quotahot-bak` 备份。想手动运行或装到系统目录也可以：

```bash
sudo cp dist/quotahot /usr/local/bin/
quotahot                         # 任何目录下都能跑
quotahot serve                   # 显式启动服务，与无参数相同
quotahot --help                  # 打印主程序用法，不启动服务
PORT=9000 quotahot               # 临时换端口
```

想连 Node 都不装，见下面的第三种。

要拷给别人就打个包，里面是同一个可执行文件加一份说明：

```bash
npm run build             # 一次完成所有构建，并产出 dist/、SEA 可执行文件和 tar/zip 包
```

压缩包内带 `install.sh`，Linux 用户解压后直接运行它即可。Windows 上没有 shebang 这套约定，
包里另附了一个 `start.cmd`，内容就是用 node 拉起同一个文件。

从源码仓库里装也可以，`bin` 指向的是 ESM 那份产物：

```bash
npm run build && npm i -g .   # 同样得到 quotahot 命令
```

**不依赖 Node 的单文件可执行**：

```bash
npm run build             # 同时产出 release/quotahot（Windows 上是 .exe）
```

用的是 Node 自带的 SEA：复制一份 node 二进制，把打包好的服务端塞进它预留的空位（塞的正是上面那个 1.7 MB 的文件）。产物放在 `release/` 而不是 `dist/`，因为 vite 每次构建都会清空 `dist/`。代价是产物约 120 MB——那是 Node 运行时本身的体积。**不能交叉编译**，要哪个平台的可执行文件就得在对应平台上运行 `npm run build`；macOS 上还需要 `codesign`（脚本已经代劳）。所以它不会放进 tar/zip 压缩包里。

## 长时间运行

Linux 优先使用安装脚本，它已经完成了复制、生成 systemd 用户单元、启用和启动：

```bash
./scripts/install.sh               # 源码仓库中，先 npm run build
# 或者在解压后的分发包目录运行 ./install.sh
loginctl enable-linger $USER      # 让它在用户未登录时也继续跑
journalctl --user -u quotahot -f
```

脚本会把当前 `node` 的绝对路径写进 `ExecStart`，并把 `~/.quotahot/bin` 放进服务 PATH，因此通过 nvm 安装的 Node 也不会依赖 systemd 的精简 PATH。
仓库里的 `quotahot.service` 仍可作为手动配置模板；手动安装时要保证其中的二进制路径与实际位置一致。

macOS 用 launchd，把下面这段存成 `~/Library/LaunchAgents/com.quotahot.plist` 后 `launchctl load -w` 它：

```xml
<key>ProgramArguments</key>
<array><string>/usr/local/bin/quotahot</string></array>
<key>EnvironmentVariables</key><dict><key>PORT</key><string>8686</string></dict>
<key>RunAtLoad</key><true/>
<key>KeepAlive</key><true/>
```

Windows 用 [nssm](https://nssm.cc/) 装成服务（首次安装可用 `nssm install quotahot node C:\quotahot\quotahot`），或者在任务计划程序里建一个"登录时触发"的任务。已有 Windows 服务或 macOS LaunchAgent 请更新原服务中的程序路径，不要重复注册。

`Restart=always` 配合 SQLite 恢复，能够扛住进程崩溃和机器重启，另外两个平台的 `KeepAlive` 与 nssm 的自动重启是同一个意思。

#### 重启之后自己回来

进程被拉起来只意味着 Web 服务活着，**调度要不要跟着跑，看的是你上一次的意思**：在界面上点过「启动」之后，`~/.quotahot/config.json` 里的 `autoStart` 会被置为 `true`，下次进程起来就自动把调度恢复到停机前的状态（纳入哪几个账户也一并记在 `autoStartIds` 里，空数组表示全部可保活账户）；你自己点「停止」才会把它置回 `false`。

服务收到 `SIGTERM` 时内部那次停止**不算**你按的停止，因此不会改动这个开关——否则 systemd 每次重启前都会先把它关掉，重启之后就再也不会自己跑起来了。

这个开关没有做成设置面板里的选项，因为它记的是状态而不是偏好；在界面里保存设置也不会把它清掉。无人值守的部署可以直接把 `"autoStart": true` 写进 `config.json`，不必先开一次界面：

```bash
quotahot  # 启动日志里会打出「自动启动: 开（沿用上次的运行状态）」
```

少了这一层，保活服务会被 `Restart=always` 老老实实拉起来、然后停在那儿一条都不发，而界面上每个账户的「下次发送」倒计时照走不误（它读的是库里的 `nextDue`），所以这种断最不容易被发现。

### 状态库

状态存在 `~/.quotahot/state.db`（`QUOTAHOT_DATA_DIR` 可改）。库里所有时刻列存的是 **ISO-8601 UTC 文本**而不是毫秒数，直接查就能读：

```bash
sqlite3 ~/.quotahot/state.db \
  "SELECT account_id, datetime(next_due_at, 'localtime') AS 下一拍, used_percent FROM account_state"
```

文本是定长的 UTC 格式，所以字典序就是时序，`ORDER BY`、`<`、`BETWEEN` 都照常用。`NULL` 表示“还没有这件事”（没排过期、没发过、没查到窗口）。

1.0.1 及更早版本建的库存的是毫秒数，**升级时删掉 `state.db` 重新开始**：程序不带迁移，留着旧库会让同一列里混着两种表示。状态和日志靠下一轮额度查询、下一次发送就能重新攒出来，只是删库之后所有账户都没有已排好的下一拍，会当成全新起跑重新排。

## 说明

- 账户保存在程序自己的目录（默认 `~/.quotahot/accounts/`），文件权限 `0600`，写入走临时文件加改名，中途断电不会留下半个文件。卡片上的**移除**只删这份拷贝，不影响原始凭证。
- 访问令牌会在过期前 10 分钟自动刷新，并原子回写到账户目录里的文件；刷新响应没带新的 `id_token` 时保留旧的，不会把它清空。设为**跟随客户端**的账户不走这条路，改为从原客户端的凭证文件同步，见[续期方式](#续期方式自动刷新还是跟随客户端)。
- 401/403 会立即停掉对应账户，避免持续撞墙；其他账户不受影响。
- 429 不视为失败，因为它本身就携带了下一次调度所需的重置时间。
- 发送模型在主面板下拉选择，Claude / Codex 各一项。保存后从下一拍起生效。下拉里是**这个账户真正能用的模型**：`GET /api/models` 会拿一个可用账户去问上游目录接口——Codex 走 `chatgpt.com/backend-api/codex/models?client_version=…`（隐藏的内部模型和不支持 API 的会被滤掉，其余按上游给的 priority 排），Claude 走 `api.anthropic.com/v1/models`。结果按 provider 缓存 30 分钟；换了账户或上游上新，点**刷新模型**跳过缓存重查。
- 查不通（没有该类账户、令牌过期、目录接口拒绝）时退回 `src/shared/models.ts` 里的内置清单，并在下拉框旁写明原因，不会变成空列表。清单只是建议不是白名单，上游发布新模型也可以通过“自定义…”手填 ID。
- Codex 的默认模型是 `gpt-5.6-luna`，Claude 是 `claude-sonnet-5`。已保存过的 `~/.quotahot/config.json` 会覆盖默认值，不会被新默认值改写——想用上新默认值，在界面里改一下或删掉旧配置。
- **额度刷新（分钟）**控制后台自动查询的周期，默认 10 分钟；改成 0 就只在点“查询额度”时查。它是只读的，不会消耗额度。**只在每日时段内刷新**，时段外这条循环睡着不发请求，到点开窗自己醒过来。周期改动从下一轮开始生效；调度器等待期间不另外查额度，直接用这条循环写进库的成果改期。
- **客户端核对（分钟）**控制多久核对一次本机客户端在用哪个账户，默认 5 分钟，改成 0 就不再核对。它只读本机的凭证文件，不发网络请求，见[本机在用](#本机在用这台电脑现在用的是哪个账户)。
- 代理在主面板配置后保存即生效，无需重启。所有出站请求都会走它，包括上游对话接口和 OAuth 令牌刷新。只接受 `http://` 与 `https://`；`socks5://` 会被直接拒绝。地址非法时前后端都会拦截，并保留之前可用的代理设置，不会悄悄退回直连。
- **忽略代理**遵循 `NO_PROXY` 语义，逗号分隔，支持 `example.com`、`.example.com`、`example.com:8443`、`*` 等写法。仅在配置了代理时生效。
- 这类保活自动化在两家服务条款下都可能被视为异常流量模式，账号存在风险，请自行权衡。
