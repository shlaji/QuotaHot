## 检查清单的用途：“需求文字的单元测试”

**核心概念**：检查清单是**需求编写的单元测试**，用于验证特定领域需求的质量、清晰度和完整性。

**不用于验证或测试实现**：

- ❌ 不是“验证按钮能否正确点击”
- ❌ 不是“测试错误处理是否有效”
- ❌ 不是“确认 API 返回 200”
- ❌ 不是检查代码或实现是否符合规格说明

**用于验证需求质量**：

- ✅ “是否为所有卡片类型定义了视觉层级需求？”（完整性）
- ✅ “是否用具体尺寸和位置量化了‘突出显示’？”（清晰度）
- ✅ “所有交互元素的悬停状态需求是否一致？”（一致性）
- ✅ “是否为键盘导航定义了无障碍需求？”（覆盖度）
- ✅ “规格说明是否定义了标志图片加载失败时的处理方式？”（边界情况）

**类比**：如果把规格说明看成用自然语言编写的代码，检查清单就是它的单元测试套件。你要测试的是需求是否表达得当、完整、无歧义，并且已具备实现条件，而不是实现是否有效。

**归属与复选框生命周期**：

- 本命令生成的自定义检查清单是由评审者负责的需求质量评审产物。
- `[x]` 表示评审者已判定相应需求质量标准得到满足。
- `[x]` 不表示实现工作已完成。
- 本命令用于生成或追加检查项，绝不能将生成的检查项标记为 `[x]`。
- 只有评审者明确提出要求时，代理才能协助评估检查项。
- `checklists/requirements.md` 是独立的内置规格质量检查清单，由 `/speckit.specify` 和 `/speckit.clarify` 维护；不得将这一例外套用到此处生成的自定义检查清单。

## 用户输入

```text
$ARGUMENTS
```

继续之前，你**必须**考虑用户输入（如果非空）。

## 执行前检查

**检查扩展钩子（生成检查清单之前）**：
- 检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，读取该文件并查找 `hooks.before_checklist` 键下的条目。
- 如果 YAML 无法解析或内容无效，不得静默跳过：告知用户无法读取 `.specify/extensions.yml`（附上解析器错误），且未检查任何钩子，包括其中注册的所有强制钩子（`optional: false`），然后正常继续。
- 过滤掉 `enabled` 显式为 `false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 对每个剩余钩子，**不要**尝试解释或求值其 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或该字段为 null 或空值，则视为可执行。
  - 如果钩子定义了非空的 `condition`，则跳过该钩子，将条件求值交给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **强制钩子**（`optional: false`）：
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    等待钩子命令返回结果后，再继续执行步骤部分。
    ```
    输出上述块后，你必须实际调用该钩子，等待执行完成后才能继续。调用方式应与你在当前代理或会话中自行运行该命令的方式相同（实际调用形式可能不同于上面显示的字面 `{command}` ID，例如技能模式代理会使用 `/skill:speckit-...` 或 `$speckit-...`）。仅输出该块并不会运行钩子。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，则静默跳过。

## 执行步骤

1. **准备**：在仓库根目录运行 `python3 .specify/scripts/python/check_prerequisites.py --json --template checklist-template`，并从 JSON 中解析 FEATURE_DIR、AVAILABLE_DOCS 列表和 TEMPLATE_CONTENT。
   - 所有文件路径都必须是绝对路径。
   - 如果参数包含单引号，例如 "I'm Groot"，请使用转义语法，如 'I'\''m Groot'（如果可行，也可使用双引号："I'm Groot"）。

2. **如果存在**：加载 `.specify/memory/constitution.md`，获取项目原则和治理约束。

3. **澄清意图（动态）**：根据上下文提出最多三个初始澄清问题，不得套用预设问题目录。这些问题必须：
   - 根据用户的表述，以及从 spec/plan/tasks 中提取的线索生成。
   - 仅询问会实质改变检查清单内容的信息。
   - 如果 `$ARGUMENTS` 已明确回答某个问题，则逐一跳过相应问题。
   - 优先追求精确，而不是覆盖面广。

   生成算法：
   1. 提取线索：功能领域关键词（例如认证、延迟、UX、API）、风险信号（“关键”“必须”“合规”）、利益相关方提示（“QA”“评审”“安全团队”），以及明确的交付物（“a11y”“回滚”“契约”）。
   2. 将线索归为候选关注领域，最多 4 个，并按相关性排序。
   3. 如果未明确说明，识别可能的使用者和使用时机（作者、评审者、QA、发布）。
   4. 找出缺失维度：范围广度、深度或严谨程度、风险重点、排除边界、可衡量的验收标准。
   5. 从以下类型中选择并拟定问题：
      - 细化范围（例如：“是否应包含与 X 和 Y 的集成衔接点，还是仅关注本地模块的正确性？”）
      - 确定风险优先级（例如：“这些潜在风险领域中，哪些需要设置强制准入检查？”）
      - 校准深度（例如：“这是提交前的轻量合理性检查清单，还是正式的发布准入检查？”）
      - 明确使用者（例如：“仅由作者使用，还是由同事在 PR 评审时使用？”）
      - 排除范围（例如：“本轮是否应明确排除性能调优项？”）
      - 场景类别缺口（例如：“未发现恢复流程，回滚或部分失败路径是否在范围内？”）

   问题格式规则：
   - 如果提供选项，生成紧凑表格，列为：Option | Candidate | Why It Matters（选项 | 候选内容 | 重要性说明）。
   - 最多提供 A 至 E 五个选项；如果自由回答更清楚，则省略表格。
   - 绝不要要求用户重复已经说过的内容。
   - 避免臆测类别，不得编造。不确定时，明确询问：“请确认 X 是否属于范围。”

   无法交互时的默认值：
   - 深度：标准。
   - 使用者：与代码相关时为评审者（PR），否则为作者。
   - 重点：相关性最高的两个类别。

   输出问题，标记为 Q1/Q2/Q3。收到回答后，如果仍有至少两个场景类别（替代路径、异常、恢复、非功能领域）不明确，可以再提出最多两个有针对性的追问（Q4/Q5），每个问题附上一行理由（例如“恢复路径风险尚未明确”）。问题总数不得超过五个。如果用户明确拒绝继续回答，则不再追问。

4. **理解用户请求**：结合 `$ARGUMENTS` 和澄清问题的回答：
   - 确定检查清单主题（例如安全、评审、部署、用户体验）。
   - 汇总用户明确提出的必需项。
   - 将选定的关注领域映射到分类框架。
   - 从 spec/plan/tasks 中推断缺失的上下文，不得编造。

5. **加载功能上下文**：从 FEATURE_DIR 读取：
   - spec.md：功能需求和范围。
   - plan.md（如果存在）：技术细节和依赖。
   - tasks.md（如果存在）：实现任务。

   **上下文加载策略**：
   - 只加载与当前关注领域相关的必要部分，避免整份文件原样倾倒。
   - 优先将长章节概括为简短的场景或需求要点。
   - 逐步补充信息，仅在发现缺口时追加检索。
   - 如果源文档很大，生成阶段性摘要条目，不要嵌入原文。

6. **生成检查清单**：使用 TEMPLATE_CONTENT 作为结构模板，创建“需求的单元测试”：
   - 如果 `FEATURE_DIR/checklists/` 目录不存在，则创建它。
   - 生成唯一的检查清单文件名：
     - 根据领域使用简短、能说明用途的名称（例如 `ux.md`、`api.md`、`security.md`）。
     - 格式：`[domain].md`。
   - 文件处理方式：
     - 如果文件不存在：创建新文件，检查项从 CHK001 开始编号。
     - 如果文件已存在：向现有文件追加新检查项，接续最后一个 CHK ID 编号（例如最后一项为 CHK015，则新检查项从 CHK016 开始）。
   - 绝不要删除或替换现有检查清单内容，始终保留并追加。
   - 所有新生成的检查项均保持未勾选（`[ ]`），复选框状态由评审者负责。

   **核心原则：测试需求，而不是实现**：
   每个检查项都必须从以下方面评估需求本身：
   - **完整性**：是否包含所有必要需求？
   - **清晰度**：需求是否明确、具体且无歧义？
   - **一致性**：需求之间是否相互一致？
   - **可衡量性**：能否客观验证需求？
   - **覆盖度**：是否涵盖所有场景和边界情况？

   **分类结构**：按需求质量维度分组：
   - **需求完整性**（是否记录了所有必要需求？）
   - **需求清晰度**（需求是否具体且无歧义？）
   - **需求一致性**（需求是否一致且无冲突？）
   - **验收标准质量**（成功标准是否可衡量？）
   - **场景覆盖度**（是否涵盖所有流程和情况？）
   - **边界情况覆盖度**（是否定义了边界条件？）
   - **非功能需求**（是否明确规定了性能、安全、无障碍等需求？）
   - **依赖与假设**（是否已记录并验证？）
   - **歧义与冲突**（哪些内容需要澄清？）

   **如何编写检查项：“需求文字的单元测试”**：

   ❌ **错误**（测试实现）：
   - “验证落地页显示 3 张节目卡片”
   - “测试桌面端的悬停状态是否有效”
   - “确认点击标志能跳转到首页”

   ✅ **正确**（测试需求质量）：
   - “是否明确规定了精选节目的具体数量和布局？” [Completeness]
   - “是否用具体尺寸和位置量化了‘突出显示’？” [Clarity]
   - “所有交互元素的悬停状态需求是否一致？” [Consistency]
   - “是否为所有交互式 UI 定义了键盘导航需求？” [Coverage]
   - “是否规定了标志图片加载失败时的降级处理方式？” [Edge Cases]
   - “是否为异步节目数据定义了加载状态？” [Completeness]
   - “规格说明是否为争夺注意力的 UI 元素定义了视觉层级？” [Clarity]

   **检查项结构**：
   每个检查项应遵循以下模式：
   - 使用询问需求质量的问题形式。
   - 关注 spec/plan 中已写明或尚未写明的内容。
   - 在方括号中注明质量维度 [Completeness/Clarity/Consistency/etc.]。
   - 检查现有需求时，引用规格说明章节 `[Spec §X.Y]`。
   - 检查缺失需求时，使用 `[Gap]` 标记。

   **按质量维度分类的示例**：

   完整性：
   - “是否为所有 API 失败模式定义了错误处理需求？ [Gap]”
   - “是否为所有交互元素明确规定了无障碍需求？ [Completeness]”
   - “是否为响应式布局定义了移动端断点需求？ [Gap]”

   清晰度：
   - “是否用具体的时间阈值量化了‘快速加载’？ [Clarity, Spec §NFR-2]”
   - “是否明确定义了‘相关节目’的筛选标准？ [Clarity, Spec §FR-5]”
   - “是否用可衡量的视觉属性定义了‘突出’？ [Ambiguity, Spec §FR-4]”

   一致性：
   - “所有页面的导航需求是否一致？ [Consistency, Spec §FR-10]”
   - “落地页和详情页的卡片组件需求是否一致？ [Consistency]”

   覆盖度：
   - “是否为空状态场景（没有节目）定义了需求？ [Coverage, Edge Case]”
   - “是否涵盖用户并发交互场景？ [Coverage, Gap]”
   - “是否明确规定了部分数据加载失败时的需求？ [Coverage, Exception Flow]”

   可衡量性：
   - “视觉层级需求是否可衡量、可测试？ [Acceptance Criteria, Spec §FR-1]”
   - “能否客观验证‘视觉权重均衡’？ [Measurability, Spec §FR-2]”

   **场景分类与覆盖度**（关注需求质量）：
   - 检查是否存在以下场景的需求：主要路径、替代路径、异常或错误、恢复、非功能场景。
   - 对每类场景，询问：“[scenario type] 需求是否完整、清晰且一致？”
   - 如果缺少某类场景，询问：“[scenario type] 需求是有意排除，还是遗漏？ [Gap]”
   - 涉及状态变更时，包含韧性和回滚检查：“是否为迁移失败定义了回滚需求？ [Gap]”

   **可追溯性要求**：
   - 最低要求：至少 80% 的检查项必须包含至少一个可追溯引用。
   - 每个检查项应引用规格说明章节 `[Spec §X.Y]`，或使用以下标记：`[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]`。
   - 如果尚无 ID 体系，询问：“是否已建立需求与验收标准的 ID 方案？ [Traceability]”

   **发现并解决问题**（需求质量问题）：
   针对需求本身提问：
   - 歧义：“是否用具体指标量化了‘快’这个词？ [Ambiguity, Spec §NFR-1]”
   - 冲突：“§FR-10 与 §FR-10a 中的导航需求是否冲突？ [Conflict]”
   - 假设：“是否验证了‘播客 API 始终可用’这一假设？ [Assumption]”
   - 依赖：“是否记录了对外部播客 API 的需求？ [Dependency, Gap]”
   - 定义缺失：“是否用可衡量的标准定义了‘视觉层级’？ [Gap]”

   **内容合并**：
   - 软上限：如果原始候选检查项超过 40 个，则按风险和影响确定优先级。
   - 合并检查同一需求方面、内容近似重复的检查项。
   - 如果低影响边界情况超过 5 个，则合并为一个检查项：“需求是否涵盖边界情况 X、Y、Z？ [Coverage]”

   **🚫 绝对禁止**：以下内容会将清单变成实现测试，而不是需求测试：
   - ❌ 任何以“验证”“测试”“确认”“检查”开头，后接实现行为的检查项。
   - ❌ 涉及代码执行、用户操作或系统行为的内容。
   - ❌ “正确显示”“正常工作”“按预期运行”。
   - ❌ “点击”“导航”“渲染”“加载”“执行”。
   - ❌ 测试用例、测试计划、QA 流程。
   - ❌ 实现细节（框架、API、算法）。

   **✅ 必须采用的模式**：以下模式用于测试需求质量：
   - ✅ “是否为 [scenario] 定义、明确规定或记录了 [requirement type]？”
   - ✅ “是否用具体标准量化或澄清了 [vague term]？”
   - ✅ “[section A] 与 [section B] 之间的需求是否一致？”
   - ✅ “能否客观衡量或验证 [requirement]？”
   - ✅ “需求是否涵盖 [edge cases/scenarios]？”
   - ✅ “规格说明是否定义了 [missing aspect]？”

7. **结构参考**：按照 `.specify/templates/checklist-template.md` 中的标准模板生成检查清单，包括标题、元信息部分、分类标题、归属说明、备注部分和 ID 格式。如果模板不可用，则使用：H1 标题、用途和创建时间元信息行、说明 `[x]` 表示评审者认可需求质量的归属说明、以 `##` 为标题的分类章节（内含 `- [ ] CHK### <requirement item>` 格式的行，ID 从 CHK001 开始全局递增），以及注明 `/speckit.implement` 会读取检查清单状态但不会修改标记的备注。

8. **报告**：输出检查清单文件的完整路径和检查项数量，并概述本次是新建文件还是追加到现有文件。汇总：
   - 选定的关注领域。
   - 深度级别。
   - 使用者和使用时机。
   - 已纳入的所有用户明确指定的必需项。

**重要说明**：每次调用 `/speckit.checklist` 都使用简短、能说明用途的检查清单文件名，新建文件或追加到现有文件。这样可以：

- 同时保留不同类型的检查清单（例如 `ux.md`、`test.md`、`security.md`）。
- 使用简单易记、能体现清单用途的文件名。
- 在 `checklists/` 文件夹中方便地识别和查找清单。

为避免杂乱，使用能说明用途的类型名称，并在完成后清理过时的检查清单。

## 检查清单类型与检查项示例

**UX 需求质量：** `ux.md`

示例检查项（测试需求，而不是实现）：

- “是否用可衡量的标准定义了视觉层级需求？ [Clarity, Spec §FR-1]”
- “是否明确规定了 UI 元素的数量和位置？ [Completeness, Spec §FR-1]”
- “是否一致地定义了交互状态（悬停、聚焦、激活）需求？ [Consistency]”
- “是否为所有交互元素明确规定了无障碍需求？ [Coverage, Gap]”
- “是否定义了图片加载失败时的降级处理方式？ [Edge Case, Gap]”
- “能否客观衡量‘突出显示’？ [Measurability, Spec §FR-4]”

**API 需求质量：** `api.md`

示例检查项：

- “是否为所有失败场景明确规定了错误响应格式？ [Completeness]”
- “是否用具体阈值量化了限流需求？ [Clarity]”
- “所有端点的身份认证需求是否一致？ [Consistency]”
- “是否为外部依赖定义了重试和超时需求？ [Coverage, Gap]”
- “需求中是否记录了版本管理策略？ [Gap]”

**性能需求质量：** `performance.md`

示例检查项：

- “是否用具体指标量化了性能需求？ [Clarity]”
- “是否为所有关键用户旅程定义了性能目标？ [Coverage]”
- “是否明确规定了不同负载条件下的性能需求？ [Completeness]”
- “能否客观衡量性能需求？ [Measurability]”
- “是否为高负载场景定义了降级需求？ [Edge Case, Gap]”

**安全需求质量：** `security.md`

示例检查项：

- “是否为所有受保护资源明确规定了身份认证需求？ [Coverage]”
- “是否为敏感信息定义了数据保护需求？ [Completeness]”
- “是否记录了威胁模型，并使需求与其保持一致？ [Traceability]”
- “安全需求是否符合合规义务？ [Consistency]”
- “是否定义了安全失效或安全入侵的响应需求？ [Gap, Exception Flow]”

## 反例：不应采用的做法

**❌ 错误：这些检查项测试的是实现，而不是需求：**

```markdown
- [ ] CHK001 - Verify landing page displays 3 episode cards [Spec §FR-001]
- [ ] CHK002 - Test hover states work correctly on desktop [Spec §FR-003]
- [ ] CHK003 - Confirm logo click navigates to home page [Spec §FR-010]
- [ ] CHK004 - Check that related episodes section shows 3-5 items [Spec §FR-005]
```

**✅ 正确：这些检查项测试的是需求质量：**

```markdown
- [ ] CHK001 - Are the number and layout of featured episodes explicitly specified? [Completeness, Spec §FR-001]
- [ ] CHK002 - Are hover state requirements consistently defined for all interactive elements? [Consistency, Spec §FR-003]
- [ ] CHK003 - Are navigation requirements clear for all clickable brand elements? [Clarity, Spec §FR-010]
- [ ] CHK004 - Is the selection criteria for related episodes documented? [Gap, Spec §FR-005]
- [ ] CHK005 - Are loading state requirements defined for asynchronous episode data? [Gap]
- [ ] CHK006 - Can "visual hierarchy" requirements be objectively measured? [Measurability, Spec §FR-001]
```

**关键区别：**

- 错误：测试系统是否正常工作。
- 正确：测试需求是否编写得当。
- 错误：验证行为。
- 正确：验证需求质量。
- 错误：“它是否完成了 X？”
- 正确：“是否明确规定了 X？”

## 执行后检查

**检查扩展钩子（生成检查清单之后）**：
检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，读取该文件并查找 `hooks.after_checklist` 键下的条目。
- 如果 YAML 无法解析或内容无效，不得静默跳过：告知用户无法读取 `.specify/extensions.yml`（附上解析器错误），且未检查任何钩子，包括其中注册的所有强制钩子（`optional: false`），然后正常继续。
- 过滤掉 `enabled` 显式为 `false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 对每个剩余钩子，**不要**尝试解释或求值其 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或该字段为 null 或空值，则视为可执行。
  - 如果钩子定义了非空的 `condition`，则跳过该钩子，将条件求值交给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **强制钩子**（`optional: false`）：
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    输出上述块后，你必须实际调用该钩子，等待执行完成后才能继续。调用方式应与你在当前代理或会话中自行运行该命令的方式相同（实际调用形式可能不同于上面显示的字面 `{command}` ID，例如技能模式代理会使用 `/skill:speckit-...` 或 `$speckit-...`）。仅输出该块并不会运行钩子。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，则静默跳过。
