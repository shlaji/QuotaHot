# 快速验证：微信绑定用户直连消息

本指南供实现完成后的自动化验证及获授权的非生产环境联调使用。联调不得使用生产账号或复制任何 bot token、`context_token`、AES key、签名参数或完整上游响应。没有获授权的非生产环境时，只执行自动化验证；不设置全局 readiness、Gate 0 或生产验收作为发送或发布前置条件。实际发送和 typing 仍须使用所选绑定自身已验证入站消息提供的非空白上下文。

**2026-10-25 架构切换范围**：移除持久 `quotahot_wechat` 浏览器 cookie、顶部会话/退出 UI 及逐绑定 QR 核验功能，保留按绑定 ID 解除、二维码新增/重新授权及短期 `quotahot_wechat_flow` 保护扫码轮询和取消。核验移除后的验证记录见下文；不表示真实多绑定终端投递已通过。

**历史状态（2026-10-22）**：此前固定 `client_id: ilink_bot_1` 的手动尝试得到 `upstream_failure`。2026-10-22 使用当前唯一可发送绑定及新生成的逐消息 `msg.client_id` 直发，客户端返回 `invalid_response`；未确认实收、入站身份或双绑定隔离。本次未重试发送；BrowserSkill 标签页借用等待确认超时，未再次借用。语音出站保持当前禁用状态。

## 前置条件

- Node.js 24+，仓库依赖已安装。
- 仅在执行真实联调时，准备一个专用且获授权的非生产微信/iLink 绑定身份，可沿用现有绑定；测试消息接收终端由操作者确认可用。第二个真实绑定可补强证据，但不作要求。
- QR/Gateway 测试配置仅保存在 QuotaHot 私有配置中。
- 远程访问沿用现有 Web 认证、HTTPS 反向代理和同源保护；不得向公网暴露未认证服务。

## 2. 多用户绑定和选择

1. 用 `npm run dev` 启动 QuotaHot。
2. 使用模拟 QR 响应先创建合成绑定 A；在 A 仍显示且有效时，直接从非空用户列表启动 B 的二维码授权并完成，确认 A、B 同时存在且各自可选；可选真实联调使用一个获授权非生产绑定，不要求新增真实身份。
3. 确认用户列表中有两个独立条目；点击即打开并直接向该绑定通信，没有 Contact 或独立本地 Conversation 实体、UI、API，也没有第二选择步骤。列表区保留“添加微信用户”、二维码、状态及取消操作，每个绑定提供自己的解除操作；不再显示顶部微信会话、退出入口或逐绑定 QR 核验按钮。实际连接、只读及回复上下文状态仍显示。
4. 对其中一个身份重新授权，确认仍只有一个条目且另一用户的授权、消息和状态不变。
5. 以 A 已绑定为前置条件，分别模拟新增授权取消、过期、上游失败、身份缺失/无效及凭证保存失败；每次结束后确认 A 的绑定、凭证、授权状态和消息历史均不变，失败结果不显示绑定成功。检查 B 未被创建，除非其有效身份和凭证均已成功保存。另模拟 A 重新授权的确认失败：若已停止旧 poller/worker，回滚后须恢复 A 原有收发，不能依赖确认后长期保留的 QR capability；B 不受影响。
6. 使用无持久微信 cookie 的浏览器访问实例，按部署配置完成全局 Web 认证，确认可列出、选择绑定并读取消息。模拟扫码成功后确认没有签发 `quotahot_wechat`，不以浏览器登录状态或会话到期时间驱动 UI；短期 `quotahot_wechat_flow` 仍用于后续扫码轮询和取消。
7. 确认解除提示后，对合成绑定 A 执行 `DELETE /api/wechat/bindings/{bindingId}`，确认目标来自路径而不是旧 cookie，成功返回 `status: unlinked`，只停止 A 本地收发且保留历史，B 继续工作；相同身份重新授权可恢复 A，并可查看原历史。解除不表示撤销微信上游授权。

## 3. 绑定上下文检查与可选真实联调（先入站，后回复）

每条验证都记录绑定身份的脱敏别名、操作步骤、API 结果和目标测试终端的实际结果。不要只把 HTTP 202 / iLink `ret: 0` 当作已送达。

1. 确认一个获授权非生产绑定及其测试终端可用；没有该用户已验证入站消息提供的上下文时，条目仅可查看、不可回复，不尝试无上下文直发。
2. 等待该绑定用户主动向平台发送一条文本。确认入站身份可验证且归属当前绑定；不匹配或无法判定时不得把该消息作为该绑定的上下文来源。
3. 确认服务端从这条已验证归属 A 的入站消息取得并私有保存对应 `context_token`。不得读取、复制、记录或通过 Web 提供 token 原文。QR 授权本身不提供该上下文。
4. 从该绑定条目手动回复一条唯一标记文本；不提供其他收件人 ID，不借用其他身份上下文。检查脱敏请求形状：包装为 `{ msg: message }`，`msg.from_user_id` 为空字符串，`msg.to_user_id` 等于该绑定的 `ilink_user_id`，`msg.client_id` 为新生成的唯一值；上下文必须来自该用户自己已验证的入站消息。
5. 在该绑定对应的测试终端确认实际收到回复并记录“收到/未收到/无法验证”。上游 `ret: 0`、HTTP 202 或 UI `accepted` 均不等同实收。
6. 自动化使用两个或更多合成绑定验证目标、入站归属、上下文和历史互相隔离；第二个真实绑定可用于补强实测，不将合成结果记为真实多绑定投递已测试。
7. 验证连续及并发出站的 `msg.client_id` 各自新生成且唯一，本地消息 UUID 也各自唯一但可与其不同；不覆盖记录，不凭未经验证的规则合并 BOT echo。
8. 分别记录图片、文件和视频的绑定适配结果；语音出站保持禁用，不启用或新增专项验收。
9. 用合成用例分别验证上下文缺失、为空白、入站 owner 不匹配、归属无法确认、仅有其他绑定上下文和客户端提供 token：发送与 typing 均须返回 context-required，且不发起对应上游请求。终端未收到或无法确认时如实记录该次观察，不转为全局能力或发布阻断。不得显示未经证实的“已送达”、创建联系人/第二消息目标、改用其他用户 ID 或自动重试未知结果。

## 4. 重启、失败和安全验证

1. 自动化在两个合成绑定下分别收发测试内容并正常重启 QuotaHot；可选真实恢复验证可沿用一个获授权非生产绑定。确认恢复不依赖旧 QR 轮询 capability，不新增替代核验端点；收件箱继续按实际 `connectionState`、`relogin_required`、`replyContextState` 和 `canSend` 展示连接、只读及发送行为，缺少自身有效上下文仍不得发送或 typing。
2. 确认新直连消息、附件、顺序和每用户游标均保留且无自动过期。每绑定准备超过两页历史，连续向上滚动自动加载更早页并保持阅读位置，不依赖手动按钮；无遗漏、重复或串号，切换后不混入旧请求结果；重复投递已处理消息不重复。
3. 模拟消息/媒体畸形、无法下载/解密和存储事务失败；失败项不含敏感原始内容，批次失败时游标不前移。
4. 模拟请求超时，确认状态为 `unknown` 且不自动重发；明确拒绝显示 `failed`；上游接受只显示 `accepted`。
5. 确认 HTTP 请求不能通过请求体覆盖消息收件人；切换选中绑定用户不会将旧消息或发送请求串到另一绑定。
6. 检查 API 响应、DOM、提示消息、控制台、日志和错误响应中不存在 bot token、`context_token`、AES key、上传 URL 或 CDN 加密参数。
7. 在合成数据库验证一次性直接重置：只删除 FR-019 列出的旧历史表，不读取或迁移旧 schema/历史内容；旧列结构不匹配或存在不相关未知表时，不得因此阻止对目标表的处理，也不得改动未知表和数据。确认 inbox 旧表清理、缺失的当前 inbox 表创建及 version 1 完成标记在同一事务内提交；已有 `inbox_binding_*` 数据保留；外键可能级联修改非目标数据或删表失败时回滚且不写完成标记；再次初始化不会删除新消息及附件。
8. 验证 `inbox_bindings`、`inbox_cursors`、当前 `inbox_binding_*` 表及数据、`wechat/wechat.db` 的 QR 凭证不变；既有 `wechat_sessions` 哈希表及旧行原样惰性保留。通过合成数据库与离线用例确认切换后的代码不读取、续期、新建或接受旧会话，携带旧 cookie 也不能绕过全局 Web 认证；不删除数据库文件，不清理 `state.db`、`tasks.db` 或无关文件。本指南不要求手工删除实际数据。
9. 在启用 Web 密码的离线环境中，对绑定列表、解除、消息、typing 和附件分别验证缺失/错误 Basic Auth 返回 401，合法全局认证无需持久微信 cookie；跨站 `Sec-Fetch-Site` 或无效/不匹配的 Origin 返回 403，响应 no-store。关闭认证时仍执行跨站保护。扫码轮询/取消在 flow cookie 缺失或不匹配时不得成功，仅凭 attempt ID 不足以操作；离开页面只取消待完成扫码，已有绑定继续收发。

## 5. 完成条件

当前检查完成标准是绑定目标和自身入站上下文校验、安全边界、生命周期、持久化及自动化行为符合规格，不要求生产验收或 readiness 状态。真实观察应保留日期、实际结果及限制，不能把 API `accepted` 扩展为送达或已读。
