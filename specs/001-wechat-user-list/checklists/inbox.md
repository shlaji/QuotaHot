# 微信多账号收件箱需求质量清单

**用途**：供 PR 评审者审查多账号绑定、iLink 收件箱和消息能力的需求完整性、清晰度、一致性与可验收性。
**创建时间**：2026-10-20
**功能**：[spec.md](../spec.md)

**说明**：本清单是评审者负责的需求质量评审产物。只有评审者判定对应需求质量标准已满足时才标记 `[x]`；这不表示实现已完成。
**标记含义**：`[x]` 表示需求质量标准经评审后满足，不代表实现工作完成。

**2026-10-24 修订口径**：绑定列表是唯一消息目标选择，无 Contact 或独立本地 Conversation。发送及 typing 校验所选绑定自身已验证入站消息提供的非空白上下文；缺失或归属不确定时返回 context-required，不借用其他身份或客户端 token。不设置全局 readiness、Gate 0 或生产验收前置条件；历史观察按日期保留，不等于当前实现已复验。

## 需求完整性

- [X] CHK001 - 是否明确区分二维码绑定用户和系统操作者，并明确不提供联系人或第二消息目标？ [完整性, 规格 §FR-002, §FR-006, §FR-007]
- [X] CHK002 - 是否完整规定新绑定、重复授权、身份缺失及授权信息保存失败时的结果，且说明何时可以报告绑定成功？ [完整性, 规格 §FR-002–FR-005, §FR-009]
- [X] CHK003 - 是否明确说明解绑或退出授权后，绑定摘要、消息、附件和游标各自的保留与可用状态？ [完整性, 规格 §FR-011, §FR-012, §FR-017]
- [X] CHK004 - 是否明确规定收发消息及附件的持久化范围、重启后的可用性，以及消息历史不自动过期的适用对象？ [完整性, 规格 §FR-014–FR-015]

## 需求清晰度

- [X] CHK005 - “足以区分用户的身份信息”和唯一当前绑定选择是否有明确、非敏感且可判断的展示标准？ [清晰度, 规格 §FR-005, §FR-006]
- [X] CHK006 - 是否明确界定“消息到达”“保存成功”“上游接受”与“送达/已读”的含义，避免将不同状态混为一谈？ [清晰度, 规格 §FR-014, §SC-008, 假设]
- [X] CHK007 - 是否明确规定绑定身份 ID、远端消息 ID 和上下文令牌各自的用途及 owner 关联范围，且不接受客户端 token？ [清晰度, 规格 §FR-002, §FR-010, §FR-020, 关键实体]
- [X] CHK008 - 是否明确界定五种消息类型（文本、图片、语音、文件、视频）的内容范围，以及未知或协议内部消息的需求处理边界？ [清晰度, 规格 §FR-012, §SC-007, 缺口]

## 需求一致性

- [X] CHK009 - 用户故事、FR 和成功标准是否一致支持文本、图片、文件、视频收发及既有入站语音，并保持语音出站禁用？ [一致性, 规格 §FR-008, §SC-005]
- [X] CHK010 - 重复授权与并发授权的需求是否一致说明身份去重、授权更新及既有会话/历史保留之间的关系？ [一致性, 规格 §FR-003, §FR-010, §FR-020]
- [X] CHK011 - 解绑、只读历史、不可发送和同 ID 重新绑定后的恢复要求是否彼此一致？ [一致性, 规格 §FR-020, 用户故事 4]
- [X] CHK012 - 关于不使用 AI、回复由操作者手动撰写的约束，是否在所有消息发送与异常路径中保持一致？ [一致性, 规格 §FR-016, 假设]

## 验收标准质量

- [X] CHK013 - 成功标准中的账号数量、重复授权次数、错误目标次数及恢复成功率是否有可重复且无歧义的统计口径？ [可衡量性, 规格 §SC-001–SC-006]
- [X] CHK014 - 是否能客观判定“用户可辨认”“所有内容到达所选目标”和“消息展示与发送均可验证”的验收条件，而不暗示上游未承诺的送达保证？ [验收标准, 清晰度, 规格 §SC-004–SC-007]
- [X] CHK015 - 需求是否为授权用户 ID 缺失、保存失败、重复远端消息及未知发送结果规定了明确的可观察结果？ [验收标准, 规格 §FR-005, §FR-009, §FR-017, §SC-003, §SC-008]

## 场景覆盖度

- [X] CHK016 - 主要路径与替代路径需求是否覆盖首次绑定、不同用户绑定、同身份重新授权、绑定切换及空列表？ [覆盖度, 规格 §用户故事 1, §用户故事 2]
- [X] CHK017 - 是否明确说明多个合成绑定的消息历史、目标和自身上下文隔离测试不等于真实多绑定投递证据？ [覆盖度, 规格 §SC-004, §FR-010, §FR-020]
- [X] CHK018 - 入站轮询的正常收件、重复投递、游标提交失败、授权失效、退避恢复和服务重启恢复是否都有清楚且相互一致的需求？ [覆盖度, 规格 §FR-017, §SC-008, §SC-009]
- [X] CHK019 - 图片、文件和视频的收发、既有入站语音、附件读取及部分传输失败场景是否分别有明确需求，且不要求语音出站？ [覆盖度, 规格 §FR-008, §FR-013, §SC-005]
- [X] CHK020 - 消息发送被接受、明确拒绝和结果未知三种路径是否分别定义用户可理解的状态与后续处置，且未知结果是否明确不自动重发？ [覆盖度, 规格 §FR-013, §FR-016, §用户故事 4 §5]

## 边界情况覆盖度

- [X] CHK021 - 是否明确规定并发二维码授权同一身份时，唯一记录及最新有效授权归属应达到的结果？ [边界情况, 规格 §FR-010]
- [X] CHK022 - 是否说明上游消息批次部分无效、未知消息项或媒体解码失败时，其余合法消息、消息历史与游标应如何处理？ [边界情况, 缺口]
- [X] CHK023 - 是否明确说明绑定用户在发送期间被解绑、重新授权或选择发生变化时，发送目标如何确定？ [边界情况, 规格 §FR-009, §FR-010, §FR-017]
- [X] CHK024 - 是否为永久保留的消息与媒体历史说明容量增长或操作者主动清理是否属于本功能范围？ [边界, 假设, 规格 §FR-015]

## 非功能需求

- [X] CHK025 - 是否完整定义认证令牌、上下文令牌、媒体密钥及上传参数不得暴露的边界，并说明普通日志、错误信息和用户可见内容的覆盖范围？ [安全性, 完整性, 规格 §FR-007, §FR-014, §FR-019, 缺口]
- [X] CHK026 - 是否明确规定访问控制和跨绑定的数据隔离适用于绑定列表、消息、附件、发送和 typing，且上下文缺失、空白或归属不确定时返回 context-required？ [安全性, 覆盖度, 规格 §FR-010, §FR-020]
- [X] CHK027 - 是否为轮询时限、退避上限、消息分页、媒体大小/类型限制或性能目标规定可衡量标准，或明确标注这些约束尚待协议验证？ [非功能需求, 可衡量性, 规格 §FR-017, §FR-019, 假设]
- [X] CHK028 - 是否明确区分协议参考、API 接受与有日期的终端观察，且不将真实非生产或生产验收、Gate 0、独立 readiness 作为发送或发布前置条件？ [依赖, 清晰度, 规格 §FR-020, §SC-004]

## 依赖与假设

- [X] CHK029 - 是否明确 `ilink_user_id` 是绑定唯一产品身份，并逐条验证入站 owner 与该绑定一致，而不是将 `from_user_id` 建成联系人？ [假设, 规格 §FR-007, §FR-020, 关键实体]
- [X] CHK030 - 对 iLink 消息、媒体、typing/config 与生命周期接口的协议参考，是否区分官方承诺、客户端参考行为和待非生产验证内容？ [依赖, 规格 §FR-017–FR-019, 假设]
- [X] CHK031 - 对消息/附件无限期保留及不自动清除的要求，是否记录了存储容量与后续人工管理责任的边界？ [假设, 规格 §FR-015, 缺口]

## 歧义与冲突

- [X] CHK032 - 是否一致规定语音出站保持禁用，不将其启用或专项验收引入本次范围？ [一致性, 规格 §FR-008, §SC-005]
- [X] CHK033 - 未发现服务端明确规定的媒体大小和格式限制；需求是否有意不承诺固定上限，并说明限制最终由谁/何时确认？ [歧义, 假设, 规格 §FR-012, §SC-007]
- [X] CHK034 - 是否建立需求与验收标准的统一追溯规则，使每项功能需求都能对应到可判定的验收依据？ [可追溯性, 规格 §FR-001–FR-020, §SC-001–SC-009]
