# 研究记录：微信绑定用户直连消息

**状态（2026-10-24 修订）**：用户已批准移除独立 readiness、Gate 0 和生产验收前置条件；发送与 typing 仅使用所选绑定自身已验证入站上下文。下文历史门禁结论不再作为当前规则。
**架构修订（2026-10-25）**：用户批准移除持久 QR 浏览器会话、顶部会话/退出 UI 及逐绑定 QR 核验功能，保留短期扫码流程保护，解除按绑定 ID 操作并沿用全局 Web 访问控制。历史代码证据中的浏览器会话及核验行为只描述当时实现，不是当前目标要求。
**日期**：2026-10-21
**功能规格**：[spec.md](./spec.md)

## 摘要

功能规格明确要求：同一实例支持多个二维码绑定用户，选中绑定即直接与该用户收发；无 Contact 或独立本地 Conversation 实体、UI、API。新直连消息和附件无限期保存，更早历史由向上滚动触发游标分页加载，不仅提供手动按钮。

现有代码和旧设计使用另一种身份模型：二维码绑定记录中的 `ownerIlinkUserId` 关联 bot 凭证，入站 `from_user_id` 被建模为收件人/联系人，外发目标和 `context_token` 都从该会话读取。该实现不得原样保留，也不得把旧会话重新标记为绑定用户直连消息。

### 当前结论

产品目标已明确。绑定用户必须先向平台发送消息，入站 owner 与该绑定一致，取得归属该绑定的私有 `context_token` 后才能回复或发送 typing。上下文缺失、为空白或归属无法确认时返回 context-required，不借用其他绑定或客户端提供的 token。客户端可构造请求不等于服务端接受或用户收到消息；QR 授权本身不会提供 `context_token`。

采用“绑定用户是唯一产品收件人”的目标，不设置全局验收状态控制发送或发布。2026-10-24 已记录一个获授权非生产绑定的文本及媒体终端观察，逐类保留结果和限制。多绑定产品支持不变，跨绑定隔离由自动化合成 owner 测试验证，不声称真实多绑定投递已测试；第二个真实绑定仅可补强证据。不得回退联系人或其他 ID。语音出站保持禁用，不在本次工作范围。

## 决策

### D1：产品身份边界是 QR 绑定用户

- **决策**：每个用户列表条目对应 QR 授权返回的 `ilink_user_id`。选择该条目即选择唯一的消息目标和消息历史归属。
- **理由**：这是功能规格的直接要求。当前绑定记录和 QR 授权完成流程已经以 `ownerIlinkUserId` 唯一标识一条绑定；UI 和收件箱服务需移除额外的收件人选择。
- **考虑过的替代方案**：保留按 `from_user_id` 列出的联系人、将联系人会话改名为“消息会话”、允许请求体提供接收者。均不符合“不存在联系人功能”或会产生可伪造/串发目标。

### D2：请求接受与终端观察分别记录，不作为额外准入状态

- **决策**：绑定用户须先向平台发来消息；只有入站 owner 与该绑定一致后，才可使用对应入站消息的私有非空白 `context_token` 回复或发送 typing。不得把可构造请求或 `accepted` 视为投递；非生产终端观察按日期、绑定数量及媒体类型分别记录，不控制发送或发布，语音出站不在范围。
- **理由**：iLink 服务端没有公开完整规范。Tencent 客户端实现显示部分字段可选，但没有服务端保证。
- **考虑过的替代方案**：以全局 Gate 0/readiness 或生产验收控制发送。2026-10-24 用户已批准移除：该状态不能替代逐绑定上下文校验。将 `sendmessage` 成功宣称为送达同样不可取，上游接受不证明终端收到，重试也可能产生重复消息。

### D3：私有上下文只可关联到已验证的绑定用户

- **决策**：回复及 typing 只使用绑定用户主动发来的、owner 匹配的入站消息所携带的 `context_token`，持久化键只能是对应绑定用户身份。没有该绑定入站消息、token 缺失、为空白或无法证明归属时返回 context-required；不接受客户端 token。`context_token`、`bot_token`、AES key、CDN 参数不能出现在 DTO、DOM、URL、普通日志或错误信息中。
- **理由**：协议客户端建议回复时携带对应入站消息的 `context_token`；QR 授权不提供该上下文，不能借用其他联系人或绑定的上下文。
- **考虑过的替代方案**：复用“最近活跃联系人”的 token 或把入站发送者自动建成目标。拒绝：会引入规格禁止的第二身份层，或把消息发给错误的人。

### D4：直接重置旧历史表，不迁移 schema 或历史内容

- **决策**：首次切换到新直连结构时，只删除 `wechat/conversations.db` 的 `wechat_conversations`、`wechat_messages`，以及 `wechat/inbox.db` 的旧 `inbox_contacts`、`inbox_messages`、`inbox_contexts`、`inbox_attachments`、`inbox_items`、`inbox_chunks`。不检查旧表列结构、不执行 schema 转换、不复制或恢复旧历史。inbox 库只创建缺失的当前结构，已有的 `inbox_binding_*` 表及数据不重建。保留现有的一次性完成标记语义；已完成标记的数据库绝不再次清理，避免删除切换后新增的历史。
- **理由**：用户明确表示不需要 schema 迁移且历史数据无需保留。旧身份也无法安全映射到新绑定消息。必须保留 `inbox_bindings`、`inbox_cursors`、所有非目标表及 `wechat/wechat.db` 的 QR 凭证；2026-10-25 修订后，既有 `wechat_sessions` 哈希表及旧行只惰性保留，不读取、续期、新建或接受旧会话。保留表不等于保留会话功能；不删除数据库文件，不清理 `state.db`、`tasks.db` 或其他无关文件。
- **考虑过的替代方案**：保留或重映射旧历史、验证旧表结构后再清理、遇到未知/无关表时拒绝整个重置，均不采用。按表名单直接删除，未知或不相关表保持原样；后续启动保留当前结构中新增的消息和附件。

### D4a：按数据库事务重置并保护外键关联数据

- **决策**：每个数据库独立执行一次重置事务；先按固定顺序检查删除名单与库内外键依赖，再在事务中删除指定旧表、创建缺失的 inbox 当前表并写入完成标记。已存在的 version 1 完成标记继续表示该库已完成一次性旧表清理，不升级或重置该标记。任一删表、建表或提交失败时回滚当前数据库，且不写入完成标记；另一数据库按自身标记独立处理。
- **理由**：当前启动流程在 `main.ts` 中先调用两库重置，随后 `WechatInboxStore` 创建 `INBOX_SCHEMA`；当前 `migrate.ts` 已使用每库 SQLite 事务和 version 1 标记。SQLite 官方文档指出，外键开启时 `DROP TABLE` 会隐式删除表内行并执行外键动作（包括可能对引用表执行 `ON DELETE CASCADE`）。显式事务可以回滚未提交的 DDL，但不能防止错误的外键级联。因此必须确保删除不会影响白名单以外的数据；若存在指向删除目标的外部外键关系，当前库事务失败关闭，而不是级联删除保护数据。
- **考虑过的替代方案**：关闭外键后强行 DROP 会留下可能失效的引用；无条件开启外键 DROP 又可能级联删除非目标数据，均不采用。检查外部依赖并事务回滚可保留目标表名单与现有数据边界。
- **权威依据**：[SQLite `DROP TABLE`](https://www.sqlite.org/lang_droptable.html)、[SQLite Foreign Key Support §4.3](https://www.sqlite.org/foreignkeys.html#fk_actions) 与 [§5](https://www.sqlite.org/foreignkeys.html#fk_schemacommands)、[SQLite Transactions](https://www.sqlite.org/lang_transaction.html#transactions)、[SQLite `PRAGMA foreign_keys`](https://www.sqlite.org/pragma.html#pragma_foreign_keys)。

### D4b：本次重置不改变操作者 API 契约

- **决策**：保留现有 `contracts/operator-inbox.openapi.yaml` 和 iLink 传输参考，不因本地启动期历史表重置变更 endpoint、请求或响应字段。
- **理由**：FR-019 只改变旧本地数据的生命周期；消息及绑定 API 的外部可观察契约不变。数据表重置边界和验证结果记录在本计划、数据模型与快速入门中。
- **考虑过的替代方案**：新增 API 端点暴露重置状态或清理历史结果，没有规格需求且会扩大外部契约，不采用。

### D5：消息与媒体沿用手动收发和持久化约束

- **决策**：适配既有文本、图片、文件、视频及入站语音处理；人工发送，不接入 AI；新直连消息及附件无限期保存，向上滚动加载更早历史；游标与批次消息原子保存；未知结果不自动重发。语音出站保持当前禁用状态，本次不启用、不新增语音工作。
- **理由**：这些要求来自既有微信收件箱范围及功能规格，并符合凭证安全和可验证行为原则。
- **考虑过的替代方案**：将任何上游响应都标成送达、失败时自动重试、仅保留短期消息。均无法满足可审计和持久化要求。

### D6：iLink 出站客户端 ID 是逐消息唯一标识

- **决策**：请求包装为 `{ msg: message }`，`msg.from_user_id: ""`、`msg.to_user_id: <当前绑定用户 ilink_user_id>`；每条发送生成新的唯一 `msg.client_id`，不接受 Web 覆盖。
- **理由**：用户已澄清 `client_id` 是每条发送消息的 ID。当前 `sender.ts` 已逐次生成 `randomUUID()`，`IlinkBotClient.sendMessage` 已包装 `{ msg: message }`，应保留这一行为而非改成常量。
- **考虑过的替代方案**：跨消息共用固定 ID 或把 ID 放在请求根级，均违反当前契约；逐消息唯一不等于已证明上游幂等。

### D7：本地消息身份与上游客户端 ID 分离

- **决策**：每条本地消息使用独立 `Message.id`，可与逐消息 `client_id` 不同；状态更新及回显关联均限定 owner，实际 BOT echo 字段和语义仍须非生产证据，不得猜测合并。
- **理由**：当前实现逐次生成随机 `client_id`，应保留逐消息唯一性，并验证连续/并发发送不会覆盖；本地主键与传输层标识不必相同。
- **考虑过的替代方案**：按最近时间或相同内容猜测回显归属。并发发送或相同内容会导致误合并，拒绝采用。

### D8：新增 QR 授权是非破坏性的独立操作

- **决策**：即使已有绑定，使用者也可直接开始另一轮 QR 授权。仅当授权身份有效且凭证保存成功时，才按身份新增或更新对应绑定；取消、过期、失败、身份无法确认或凭证持久化失败都不得改变其他绑定及其凭证、授权状态和消息历史。成功授权新身份只增加该身份，不要求先退出或解绑。
- **理由**：规格 FR-001、FR-004、FR-021 和 SC-009 明确要求已有绑定可保留并同时新增用户；现有 QR 流程按授权身份保存/更新绑定，因此应复用该流程及其身份键，不以“当前只有一个活动绑定”为前提。
- **考虑过的替代方案**：先退出/解绑再授权、授权启动时替换当前绑定、失败时清理已有身份，均会破坏规格要求的既有授权和历史。新增用户复用既有 QR 启动、轮询、取消及按身份持久化绑定的边界；2026-10-25 的 D9 另外移除成功响应中的持久浏览器会话语义，并调整绑定管理路由。

### D9：移除持久浏览器会话，保留短期扫码保护（2026-10-25）

- **决策**：QR 确认只保存或更新绑定，不签发或要求持久 `quotahot_wechat` cookie；保留短期 `quotahot_wechat_flow`，用于验证扫码轮询与取消。绑定列表、逐绑定解除、消息、typing 和附件统一沿用全局 Web `accessGuard`、按部署配置启用的 Basic Auth 及同源/跨站校验。解除目标使用 `DELETE /api/wechat/bindings/{bindingId}` 的路径绑定 ID，不从旧 cookie 推导；成功回执为 `status: unlinked`。
- **界面与生命周期**：添加用户、二维码及取消在列表区展示，每个绑定独立提供解除；移除顶部微信会话及退出操作。关闭页面或取消待完成扫码不停止已有绑定；明确解除才停止指定绑定的本地收发，保留历史、不影响其他用户，也不代表撤销上游授权。
- **存储决定**：既有数据库中的 `wechat_sessions` 哈希表及旧行原样惰性保留；切换后的实现不读取、续期、新建或接受旧会话，不以删库或清表完成会话移除。
- **理由与替代方案**：实例操作者已经受全局 Web 访问控制保护，QR 确立的是平台与绑定用户之间的通信关系，不应再成为浏览器访问绑定管理的第二登录门槛。继续按“当前浏览器身份”解除会与多绑定列表目标冲突；完全移除 flow cookie 则会丢失扫码尝试的独立轮询/取消保护，均不采用。
- **历史实现核对（2026-10-25，核验取消前）**：当时首次检查仍有持久 cookie、旧 `/session`、单数 `/binding` 和会话存储读写；同日后续源码复核记录这些入口及读写被移除，并曾提供按绑定 ID 的核验和解除。旧核验端点 `POST /api/wechat/bindings/{bindingId}/check` 仅为当时快照，现已由 D10 取消，不是当前 API 或使用步骤，也不构成当前测试通过证据。既有 `wechat_sessions` 表及旧行惰性保留的决定不变。

### D10：移除仅依赖进程内 QR capability 的逐绑定核验（2026-10-25）

- **决策**：用户明确取消逐绑定核验，移除其 API、按钮、专用状态及扫码确认后长期保留的 QR capability。不以另一种核验或伪健康端点替代，不为此持久化 QR capability。
- **理由**：旧核验只是重新轮询进程内存保留的扫码 capability；服务重启后它会消失，即使持久绑定凭证和消息仍在，也无法继续该核验。因此其结果不能表示收件箱的实际连接或发送能力，旧源码及界面观察不能证明保留该功能合理。
- **保留边界**：二维码新增/重新授权、短期 flow-cookie 轮询/取消保护、按路径解除、owner generation/drain、启停及确认失败回滚均保留。若确认失败前已停止旧 poller/worker，须恢复原有通信，不依赖已移除的长期 capability 缓存。旧会话哈希保留及全局访问守卫规则不变。
- **运行时状态**：保留收件箱实际 `connectionState`、`relogin_required`、`replyContextState` 和 `canSend`，用于连接、只读及发送行为；发送和 typing 仍逐次校验所选绑定自己的有效入站上下文。QR 授权或历史核验结果不能替代这些条件。
- **验证记录**：本次仅修订文档，未运行测试、构建或浏览器验证；取消后的最终验证结果由实现方另行记录。

## 历史代码证据（2026-10-21）

- `src/server/wechat-login-service.ts`：QR 确认后以 `ownerIlinkUserId` 保存绑定、凭证和浏览器会话，并在同一身份重新授权时更新绑定。
- `src/server/wechat-inbox/client-response.ts`：当前解析按 `message_type` 把 USER 的 `from_user_id` 或 BOT 的 `to_user_id` 存为 `contactUserId`。
- `src/server/wechat-inbox/service.ts`：当前把解析后的消息写入绑定账号下的联系人收件人；入站上下文令牌与该联系人关联。
- `src/server/wechat-inbox/sender.ts`：当前发送目标来自会话的 `contactUserId`，并从该会话读取 token；每条发送已生成随机 UUID，客户端 `IlinkBotClient.sendMessage` 包装 `{ msg: message }`。需改目标解析，不应改为固定 ID。
- `src/server/wechat-inbox/routes.ts`、`src/shared/wechat-inbox.ts`、`src/web/wechat-inbox/InboxPane.tsx`：API DTO、路径和页面都明确暴露绑定账号后再选联系人。
- `src/server/wechat-inbox/store-schema.ts`：现有联系人表及外键须按 D4 白名单一次性清理并验证保护数据不变，不能把 schema 改写当作无数据操作。
- `src/server/wechat-inbox/poller.ts`：按绑定账号单独轮询，并在 `processUpdates` 完成后继续循环；现有事务游标/消息测试可作为重构回归基线。

核验观察：

1. QR 确认提供 `bot_token`、`ilink_bot_id`、`ilink_user_id` 和 `baseurl`；文档/类型没有证明 `ilink_user_id` 可在无入站上下文时直接作为可投递收件人。
2. sender 以给定目标填 `to_user_id`；若输入中有 `context_token` 则附带。省略该字段只说明客户端可以构造和发出请求，不说明服务端会接受或投递。
3. 协议文档建议回复时传入相应入站消息的 `context_token`；Tencent inbound 代码也从入站上下文保留 token。没有发现从 QR 绑定 ID 在无入站消息时取得这种 token 的已证实机制。
4. `getconfig` 可使用 `ilink_user_id` 并返回 typing ticket 的资料，不证明它可生成消息上下文 token。
