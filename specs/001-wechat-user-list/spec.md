# 功能规格：微信多用户直连消息

**功能分支**：`[001-wechat-user-list]`（本次未创建分支）

**创建时间**：2026-10-21

**状态**：Draft

**输入**：用户描述："发送消息不应该选择联系人，用户扫二维码后绑定成功，建立的是这个平台和用户的通信机制，发送消息就是平台给这个用户发送消息，没有联系人的功能。这个平台可以收集多个人扫描二维码授权的结果，点击每个人都可以给这个人收发消息"

**架构修订（2026-10-25）**：用户批准移除持久 QR 浏览器会话、顶部会话/退出 UI 及逐绑定 QR 核验功能；保留短期扫码流程 cookie，解除按绑定 ID 操作，统一沿用全局 Web 访问控制。收件箱继续展示实际连接、只读及回复上下文状态，不以 QR 轮询结果作为运行时绑定状态。运行时验收仍须按 [quickstart.md](./quickstart.md) 执行；本文不将文档或源码核对视为测试通过。

## 用户场景与测试 *（必需）*

### 用户故事 1 - 绑定并管理多个微信用户（优先级：P1）

平台使用者可以发起二维码授权，将多个不同的微信用户绑定到同一平台实例。已有微信绑定时，仍可直接开始另一轮二维码授权，不需要先退出、解绑或替换当前绑定。每个成功绑定的用户都独立出现在用户列表中；同一用户再次授权时沿用原有条目并更新有效授权，不重复创建。

**优先级理由**：多个用户各自建立平台与用户之间的通信关系，是后续逐人收发消息的前提。

**独立测试**：先完成用户 A 的二维码授权，再在保留 A 绑定的情况下发起并完成用户 B 的授权，确认列表同时显示两人且可分别选择；再对其中一人重新授权，确认其仍只有一个条目。

**验收场景**：

1. **假设** 实例已绑定一个用户，**当** 另一个不同用户完成二维码授权，**则** 系统新增其绑定，且原有绑定保持不变。
2. **假设** 用户列表中已有某个微信用户，**当** 该用户再次成功授权，**则** 系统复用该用户条目并更新其有效授权信息，不产生重复条目。
3. **假设** 授权未能取得有效微信用户身份，**当** 授权流程结束，**则** 系统不创建绑定，并明确告知绑定未完成。
4. **假设** 当前没有已绑定用户，**当** 使用者打开微信功能，**则** 系统展示空状态和开始二维码授权的入口。
5. **假设** 当前已有一个或多个有效绑定，**当** 使用者需要添加另一个微信用户，**则** 页面仍提供开始二维码授权的入口；取消、过期或失败不会退出、删除或改变任何已有绑定。
6. **假设** 使用者已通过实例的全局 Web 访问控制且没有持久微信浏览器 cookie，**当** 打开绑定列表、选择绑定、读取消息、解除绑定或发送消息/typing，**则** 系统不要求再次扫码登录；操作仍校验路径绑定、生命周期和所需入站上下文。
7. **假设** 列表中有绑定 A 和 B，**当** 使用者解除 A，**则** 只停止 A 的收发并保留其历史，B 不受影响；关闭页面或取消待完成扫码均不等同解除 A。

---

### 用户故事 2 - 选择绑定用户并直接收发消息（优先级：P1）

平台使用者从绑定用户列表中选择一个用户，即可查看与该用户直接对应的消息，并向该用户发送消息。平台不提供联系人或联系人会话列表，也不要求使用者在绑定用户之后再选择其他消息对象。

**优先级理由**：使用者需要通过选择绑定用户确定收发对象；额外的联系人层会错误表达平台与用户之间的直接通信关系。

**独立测试**：使用两个绑定用户的自动化合成数据，分别模拟首次入站和保存各自私有上下文后回复，验证仅显示当前绑定用户的消息且上下文/目标不串线。真实终端观察单独按日期记录，不作为发送或发布前置条件，也不以合成测试声称真实多绑定投递已验证。

**验收场景**：

1. **假设** 已绑定多个微信用户，**当** 使用者打开用户列表，**则** 每个绑定用户各显示一个可选择的条目，且不显示联系人选择或联系人会话列表。
2. **假设** 使用者选择其中一个绑定用户，**当** 查看消息，**则** 系统只显示该绑定用户对应的收发消息。
3. **假设** 使用者已选择一个绑定用户，且该绑定已收到可验证归属的用户消息并取得该入站消息对应的私有 `context_token`，**当** 手动发送文本、图片、文件或视频，**则** 系统使用该绑定自己的上下文直接回复所选绑定用户，无需联系人或本地 Conversation 选择；缺少该绑定的入站上下文或无法验证归属时 MUST 拒绝发送；语音出站保持禁用，不在本次范围。
4. **假设** 任一绑定用户发送文本、图片、语音、文件或视频给平台，**当** 消息到达，**则** 系统将消息显示并保存到该绑定用户对应的消息记录中。
5. **假设** 当前没有选中有效绑定用户，**当** 使用者尝试发送消息，**则** 系统拒绝发送并说明无法确认发送对象。
6. **假设** 两个绑定用户均有消息，**当** 使用者在两者之间切换，**则** 当前消息记录和后续发送目标随所选用户切换，不发生串用。

### 用户故事 3 - 重启后继续查看消息记录（优先级：P1）

平台使用者可以查看每个绑定用户的收发历史。新直连消息及附件无限期保存，不自动过期；向上滚动消息区域时按游标加载更早历史。平台重启后，已保存的消息及附件仍可查看，且重复接收的同一条远端消息不会重复展示。

**优先级理由**：消息记录是用户与平台之间通信的连续上下文，不能因服务重启或重复轮询而丢失或重复。

**独立测试**：为两个绑定用户保存超过两页的消息及附件，重启后分别向上滚动加载更早历史，并重复投递已处理的消息，确认历史和附件保留、无重复且不串号。

**验收场景**：

1. **假设** 绑定用户已有已保存的收发消息，**当** 平台重启后使用者重新选择该用户，**则** 其历史消息仍可查看。
2. **假设** 平台再次收到已处理的远端消息，**当** 系统更新对应用户的消息记录，**则** 不会新增重复消息。
3. **假设** 一个入站批次中有一条无法解析的消息和其他有效消息，**当** 系统处理该批次，**则** 无法解析的消息以不暴露敏感内容的失败提示记录，其他有效消息仍可保存。
4. **假设** 当前绑定用户的历史超过一页，**当** 使用者向上滚动至历史边界，**则** 系统按游标加载更早消息并保持阅读位置，不依赖手动“加载更早”按钮；切换绑定后不得混入旧请求结果。

---

### 用户故事 4 - 识别授权与收发状态（优先级：P2）

平台使用者可以辨认每个绑定用户，并获知授权、连接及消息收发结果。授权、连接或消息失败时，平台明确显示失败状态，不将未完成操作报告为成功，也不影响其他绑定用户继续工作。

**优先级理由**：多个独立绑定需要清晰区分状态，单个用户的异常不应使其他用户的通信情况不可见。

**独立测试**：通过模拟的授权、连接和收发成功/失败结果验证状态展示，并确认一个用户的失败不会改变其他用户的记录或状态。

**验收场景**：

1. **假设** 某个用户授权或保存未成功，**当** 流程结束，**则** 系统显示未完成或失败，不显示绑定成功。
2. **假设** 一个绑定用户的消息连接失败，**当** 使用者查看列表及其他用户，**则** 该用户显示相应状态，其他用户的绑定和收发不受影响。
3. **假设** 消息发送成功或失败，**当** 操作结束，**则** 系统在所选用户的消息记录中明确呈现相应结果。
4. **假设** 列表展示绑定用户，**当** 使用者查看身份和授权状态，**则** 信息足以区分用户，但不显示可直接用于认证的令牌或密钥。

### 边界情况

- 同一用户的多个二维码授权流程同时完成时，最终只能保留一条该用户绑定，且授权信息必须归属该身份。
- 授权响应缺少有效用户 ID，或保存授权信息失败时，不得显示绑定成功或留下无法归属的绑定。
- 当前选中用户已解绑、授权失效或在发送前发生切换时，系统不得将消息发给其他用户。
- 一个用户的入站消息或媒体永久无法解析、下载或解密时，应隔离该失败项并继续处理同批其他有效消息；不得暴露敏感原始数据。
- 数据持久化失败时，不得推进接收游标或报告消息已保存，避免消息丢失。
- 同一远端消息重复到达时，不得重复显示；绑定用户之间即使消息标识相同，也不得合并消息。
- 关闭页面、切换页面或缺少旧持久浏览器 cookie 不停止已有绑定收发；只有明确解除指定绑定或绑定自身授权/连接失效才改变对应能力，历史记录不随解除删除。
- 短期 `quotahot_wechat_flow` 缺失或不匹配时，不得仅凭 attempt ID 轮询或取消扫码；该 cookie 不授予绑定列表、解除或消息访问能力。
- 用户列表为空时，应继续提供清晰的二维码授权入口。
- 用户列表非空时，也必须提供添加微信用户的入口；开始新增授权不得要求先退出或解除当前绑定。

## 需求 *（必需）*

### 功能需求

- **FR-001**: 系统 MUST 支持在同一平台实例中绑定多个不同的微信用户；已有绑定时，使用者 MUST 能直接发起另一轮二维码授权，不得要求先退出、解除或替换已有绑定。
- **FR-002**: 每次二维码授权成功后，系统 MUST 以授权返回的有效微信用户 ID 识别用户；已有身份复用原绑定并更新有效授权，未出现过的身份创建新绑定。
- **FR-003**: 授权未取得有效微信用户 ID 或无法保存授权信息时，系统 MUST 不创建或报告成功的绑定，并向使用者说明未完成。
- **FR-004**: 系统 MUST 展示所有已绑定用户，每个微信用户 ID 至多对应一个条目；无论当前是否已有绑定，页面 MUST 提供发起二维码授权的入口。无绑定用户时 MUST 同时展示空状态。
- **FR-005**: 用户列表 MUST 提供足以区分绑定用户及辨认其授权状态的信息，且 MUST NOT 展示可用于认证的令牌或密钥。
- **FR-006**: 使用者 MUST 能直接从绑定用户列表选择消息对象；选中用户后，系统 MUST 展示并发送该绑定用户的消息。
- **FR-007**: 系统 MUST NOT 提供 Contact 或独立本地 Conversation 实体、UI 或 API；发送消息的目标 MUST 仅由当前选中的绑定用户决定。
- **FR-008**: 系统 MUST 支持平台使用者与绑定微信用户双向收发文本、图片、文件和视频，沿用既有入站语音处理；语音出站 MUST 保持当前禁用状态，不在本次实现或验收范围。
- **FR-009**: 当系统无法确认有效的当前绑定用户或该用户的发送能力时，系统 MUST 拒绝发送并说明原因，不得改发给其他用户。
- **FR-010**: 系统 MUST 将消息和收发状态关联到唯一的绑定用户；切换用户后，消息展示和发送目标 MUST 与当前选择一致。
- **FR-011**: 系统 MUST 按绑定用户无限期保存新直连消息历史及附件；正常重启后 MUST 仍可查看，且 MUST NOT 自动过期或清除。更早历史 MUST 通过向上滚动触发游标分页加载，不得仅提供手动加载按钮。
- **FR-012**: 系统 MUST 对每个绑定用户独立接收新消息，并在服务重启后从已保存的接收进度继续；同一用户同一远端消息不得重复展示。
- **FR-013**: 入站消息或媒体永久无法解析、下载或解密时，系统 MUST 保存不包含原始敏感数据的失败提示，并继续处理同批其他合法消息；只有该批处理结果与新接收进度成功保存后才可推进接收进度，持久化失败时 MUST 保留原进度。
- **FR-014**: 系统 MUST 由平台使用者手动撰写并发送消息，MUST NOT 自动生成或自动发送回复。
- **FR-015**: 系统 MUST 明确呈现授权、连接和消息收发的成功或失败结果；一个绑定用户发生错误时 MUST NOT 覆盖其他用户的状态或阻止其收发。
- **FR-016**: 系统 MUST 支持消息输入状态及连接生命周期通知；相关通知不可用或失败时，不得阻止人工消息收发或删除绑定和历史记录。
- **FR-017**: 绑定列表、解除、消息、typing 和附件 API MUST 统一受全局 Web `accessGuard`、按部署配置启用的 Basic Auth 及同源/跨站保护约束；MUST NOT 签发、读取或要求持久 QR 浏览器会话 cookie `quotahot_wechat`。二维码轮询与取消 MUST 继续校验短期 `quotahot_wechat_flow`，其仅保护扫码流程，不作为管理或消息访问凭证。页面 MUST NOT 提供顶部微信会话或浏览器退出操作，页面关闭或切离不得停止已有绑定。
- **FR-018**: 每条出站消息 MUST 在发送时生成新的唯一 `client_id`，放在请求的 `msg.client_id`，不得跨消息共用固定值；本地消息 UUID 可与其不同。
- **FR-019**: 首次使用新直连消息结构时，系统 MUST 直接删除旧本地历史表并以当前结构重新创建，不执行旧 schema 到新 schema 的迁移，也不保留或恢复旧历史数据。删除范围仅为 `wechat/conversations.db` 的 `wechat_conversations`、`wechat_messages`，以及 `wechat/inbox.db` 的旧 `inbox_contacts`、`inbox_messages`、`inbox_contexts`、`inbox_attachments`、`inbox_items`、`inbox_chunks`；MUST 保留 `inbox_bindings`、`inbox_cursors`、当前结构的 `inbox_binding_*` 表及 `wechat/wechat.db` 中的 QR 凭证。既有 `wechat_sessions` 哈希表及旧行 MUST 原样惰性保留，MUST NOT 读取、续期、新建或接受旧会话；保留数据不表示保留认证能力。不清理 `state.db`、`tasks.db` 或其他文件。重置 MUST 仅在结构切换时执行一次；后续启动 MUST 保留新结构中新增的消息和附件。该处理不要求旧表符合可迁移的 schema；未知或不相关的表 MUST 保持不变。
- **FR-020**: 绑定用户必须先向平台发送消息，系统才能取得该入站消息对应的 `context_token` 并向其回复或发送 typing。系统 MUST 校验入站 owner 与所选绑定一致，并仅使用该绑定自己的服务端私有上下文；上下文缺失、为空白或归属无法确认时 MUST 以 context-required 拒绝发送和 typing，不得借用其他绑定、其他入站身份或客户端提供的上下文。系统 MUST NOT 增设全局 readiness、Gate 0 或生产验收作为发送或发布前置条件。
- **FR-021**: 系统 MUST 将新增微信用户的二维码授权作为独立于已有绑定退出/解除的操作；新增身份授权成功后 MUST 保留全部其他绑定及其历史，授权失败、取消、过期或无法确认身份时 MUST 不改变已有绑定。
- **FR-022**: 列表 MUST 为每个绑定提供解除操作，使用 `DELETE /api/wechat/bindings/{bindingId}`；目标 MUST 仅由路径绑定 ID 决定，不依赖浏览器会话身份。解除成功 MUST 返回 `status: unlinked`，仅停止并移除指定用户的本地有效绑定，保留其消息历史且不影响其他绑定；MUST NOT 将解除描述为撤销微信上游授权。相同身份重新授权后可恢复通信并查看原历史。

### 关键实体 *（功能涉及数据时填写）*

- **绑定用户**：由二维码授权返回的微信用户 ID 唯一标识；关联该用户的授权状态及独立通信能力。
- **消息**：平台使用者或绑定用户发送的文本、图片、语音、文件或视频；关联唯一绑定用户、方向、内容类型、时间和收发状态。
- **二维码授权流程**：一次独立的短期授权尝试，由 `quotahot_wechat_flow` 保护轮询和取消；成功后依据微信用户 ID 创建新绑定或更新现有绑定，不创建持久浏览器登录会话。

## 成功标准 *（必需）*

### 可衡量结果

- **SC-001**: 10 个不同微信用户分别完成授权后，使用者能在列表中辨认并打开全部 10 个用户，且不同用户之间绑定覆盖次数为 0。
- **SC-009**: 已有一个绑定时，使用者无需退出或解除该绑定即可发起并完成第二个不同微信用户的授权；完成后两项绑定同时可见，原绑定丢失次数为 0。
- **SC-002**: 对同一用户连续完成 10 次重新授权后，该用户在列表中仍恰好出现 1 次，且其他用户的授权和记录不变。
- **SC-003**: 使用者从列表选择一个绑定用户即可查看其消息或撰写发给该用户的消息；收件人选择只有绑定列表，不存在 Contact 或独立本地 Conversation 的 UI/API。
- **SC-004**: 在至少两个合成绑定的并行测试中，100% 的出站请求使用所选绑定目标及其自身已验证入站上下文，错误目标及跨绑定上下文使用次数为 0。真实终端结果仅按操作者确认的范围记录，不将合成隔离测试视为真实多绑定投递证据，也不要求真实验收作为发送或发布前置条件。`accepted` 不代表送达或已读。
- **SC-005**: 对文本、图片、文件和视频分别完成绑定目标的双向验收，均显示在正确用户的消息记录中；语音出站保持禁用，不作为通过条件。
- **SC-006**: 平台正常重启后，新直连消息历史及附件可查看率为 100%；超过两页的历史可通过连续向上滚动加载，无缺漏、重复或串号；重复投递已处理消息产生的重复展示数为 0。
- **SC-007**: 授权身份缺失、授权保存失败或发送对象无效时，成功误报次数为 0，且系统给出可理解的失败结果。
- **SC-008**: 用户列表和消息交互中，认证令牌或密钥的可见暴露次数为 0；一个用户失败时，其他绑定用户成功收发能力保持可用。

## 假设

- 微信授权返回的用户 ID 可在同一平台实例内稳定标识同一微信用户；该实例是绑定、消息归属和去重的边界。
- 每个被绑定用户就是一个直接消息对象；不在绑定用户与消息之间引入联系人或其他收件人层级。
- 平台使用者是消息操作人，消息由平台直接发给或接收自当前选中的绑定用户。
- 本次适配既有文本、图片、文件和视频收发及入站语音处理；不新增语音能力，语音出站保持禁用。新直连消息及附件不自动过期；旧数据仅按 FR-019 一次性清理。
- 已绑定用户重新授权时，以最近一次成功取得的授权信息为当前有效授权。
- 消息由平台使用者手动撰写；本功能不包含 AI 生成或自动回复。
- 只有明确解除指定绑定或其自身授权/连接失效会停止对应收发；关闭浏览器或离开页面不会解除绑定。解除不自动删除已保存历史，重新二维码授权可恢复通信。
- 输入状态和连接生命周期通知属于辅助能力；其失败不应中断消息收发。
- 首次切换到新直连消息结构时，旧联系人、会话及消息表中的历史内容均可丢弃；绑定授权、接收游标、当前结构数据及其他应用数据不属于可丢弃历史范围。
