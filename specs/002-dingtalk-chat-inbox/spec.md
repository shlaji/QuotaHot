# Feature Specification: DingTalk Message Inbox

**Feature Branch**: `[dingtalk-chat]`

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "我已经安装了/dingtalk-相关的skill, 需要基于这些skill的能力开发功能。web端可以搜索群和人的信息，可以对选中的人和群监听消息事件, 收到消息后显示在聊天框，可以给这个人回复消息。"

## Clarifications

### Session 2026-10-21

- Q: DingTalk 能力由哪一侧在运行时提供？ → A: 由独立部署的 DingTalk Inbox 服务负责运行时，通过受支持的 `dws` CLI 子进程调用 DingTalk 能力；QuotaHot 仅作为可选 Web 客户端，不承载该服务的业务逻辑、DWS 进程或数据存储。
- Q: 服务重启或用户离开页面后，已收到的聊天消息应如何保留？ → A: 持久化消息；服务重启或重新打开页面后可查看已有记录。
- Q: 已保存的聊天消息应保留多久？ → A: 保留最近 30 天，之后自动删除。
- Q: DingTalk Inbox 服务重启后，之前的消息监听应如何恢复？ → A: 自动恢复此前的监听；QuotaHot 重启不得影响独立服务中的监听。
- Q: 发送回复显示“成功”时，应表示钉钉已接受发送请求，还是对方已收到消息？ → A: 表示钉钉已接受发送请求，不代表对方已收到；无法确认结果时显示待确认。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 搜索并选择消息对象 (Priority: P1)

平台使用者可在 Web 端搜索 DingTalk 用户或群，查看可辨认的搜索结果，并明确选择一个目标开始查看其消息。用户与群是两种明确区分的目标类型。

**Why this priority**: 明确消息对象是启动监听和避免消息错投的前提。

**Independent Test**: 搜索一个已知用户和一个已知群，分别选择结果，确认当前消息视图始终标明其对象类型和身份。

**Acceptance Scenarios**:

1. **Given** 搜索服务可用且查询有唯一结果，**When** 使用者搜索并选择某个用户，**Then** 消息视图显示该用户的身份并可开始该对象的消息监听。
2. **Given** 搜索服务可用且查询有唯一结果，**When** 使用者搜索并选择某个群，**Then** 消息视图显示该群的身份并可开始该对象的消息监听。
3. **Given** 搜索结果为空或存在多个无法区分的候选项，**When** 使用者尝试选择目标，**Then** 系统不擅自选择对象，并说明如何缩小或修正搜索。

### User Story 2 - 接收并查看实时消息 (Priority: P1)

平台使用者可对已明确选择的用户或群开启消息事件监听。监听收到的消息会出现在对应聊天框，且能辨认消息发送者及消息属于哪个会话。

**Why this priority**: 消息到达正确的聊天框是本功能的核心价值。

**Independent Test**: 分别对一个用户和一个群开始监听，向各自发送消息，确认消息只显示在匹配的聊天框中。

**Acceptance Scenarios**:

1. **Given** 已选择一个用户且监听已就绪，**When** 该用户发送消息，**Then** 消息显示在该用户的聊天框中。
2. **Given** 已选择一个群且监听已就绪，**When** 群内出现消息，**Then** 消息显示在该群的聊天框中并标识发送者。
3. **Given** 使用者切换到另一个已选择对象，**When** 前一对象仍有消息到达，**Then** 消息归入前一对象的记录，不得出现在当前对象的聊天框中。
4. **Given** 监听尚未就绪、已停止或发生错误，**When** 使用者查看聊天框，**Then** 系统准确呈现监听状态，不将无消息误报为监听成功。

### User Story 3 - 回复收到的消息 (Priority: P2)

平台使用者可在聊天框撰写并发送文本回复。回复必须发往该聊天框对应的用户或群，不需要另选联系人或从会话列表推断收件对象。

**Why this priority**: 在查看消息的上下文中直接回复可完成基本双向沟通。

**Independent Test**: 在用户聊天框及群聊天框分别发送一条回复，确认每条回复发往当前聊天框所标识的对象，并显示可理解的发送结果。

**Acceptance Scenarios**:

1. **Given** 当前打开的聊天框已明确关联一个用户，**When** 使用者发送文本回复，**Then** 系统将其发送给该用户并在对应聊天框呈现发送结果。
2. **Given** 当前打开的聊天框已明确关联一个群，**When** 使用者发送文本回复，**Then** 系统将其发送到该群并在对应聊天框呈现发送结果。
3. **Given** 发送失败或结果未知，**When** 系统收到失败结果或无法确认投递，**Then** 系统明确显示失败或待确认状态，不得将其标记为已送达。

### Edge Cases

- 搜索期间网络不可用、服务拒绝查询或没有匹配对象时，应显示可理解的失败或空结果状态，不得伪造结果。
- 事件订阅创建失败或未进入就绪状态时，不得显示监听中，也不得自动改为轮询、联系人列表或会话列表模式。
- 多个对象同时收到消息时，每条消息必须按其真实会话身份进入各自记录；无法确认归属的消息不得展示在错误会话中。
- 重复投递的同一消息不得造成重复展示；消息乱序到达时仍应保留可理解的时间顺序信息。
- 当前对象被删除、权限撤销或服务端身份失效时，应停止将消息发送给该对象，并清楚说明需要重新授权或选择有效对象。
- 使用者离开页面或关闭服务后，监听的持续时间和恢复方式须符合经确认的运行时订阅能力；不得宣称页面关闭后仍持续监听，除非验收证据证明该行为成立。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许使用者按关键词搜索 DingTalk 用户和群，并明确区分两类搜索结果。
- **FR-002**: 系统 MUST 要求使用者明确选择唯一目标后，才可为该目标开始监听或发送消息；不得以名称相似度、结果顺序或最近使用记录自动决定目标。
- **FR-003**: 系统 MUST 在聊天视图中持续清晰标识当前目标及其类型（用户或群）。
- **FR-004**: 系统 MUST 支持使用者对明确选中的用户或群开始和停止消息事件监听，并显示启动中、就绪、停止中、已停止及失败等适用状态。
- **FR-005**: 系统 MUST 将收到的消息按事件所确认的会话身份显示在对应聊天框，并显示消息发送者及可用的发送时间信息。
- **FR-006**: 系统 MUST 提供文本消息撰写和发送能力，收件对象只能是当前聊天框已确认的目标。
- **FR-007**: 系统 MUST 将钉钉明确接受发送请求显示为发送成功，但不得据此声称对方已收到；同时区分发送失败和投递结果未知，未知结果不得显示为成功。
- **FR-008**: 系统 MUST 防止重复事件造成同一消息重复展示，并防止不同会话的消息交叉显示。
- **FR-009**: 系统 MUST 在搜索、监听和发送出现错误时，向使用者提供可理解的状态或下一步；在监听未就绪时不得声称正在接收实时消息。
- **FR-010**: 若独立服务部署环境不具备 DingTalk 搜索、事件监听或消息发送能力，服务 MUST 明确阻止相应功能进入可用状态并报告阻塞原因；MUST NOT 静默回退至联系人、会话选择或非实时轮询。
- **FR-011**: 系统 MUST 仅在当前授权及权限允许时执行搜索、监听和发送，并不得在界面中暴露认证密钥或令牌。
- **FR-012**: 系统 MUST 持久化已接收及已发送的消息，并在服务重启或用户重新打开聊天视图后恢复相应会话的消息记录。
- **FR-013**: 系统 MUST 自动删除本地持久化时间超过 30 天的已持久化入站及出站消息。
- **FR-014**: 独立 DingTalk Inbox 服务 MUST 在自身重启后自动恢复此前活动目标的消息监听；仅当新订阅进入就绪状态后，才能显示监听就绪。QuotaHot Web 服务重启、升级或停止 MUST NOT 终止、重建或改变独立服务拥有的订阅。
- **FR-015**: DingTalk Inbox 能力 MUST 作为独立构建、部署、配置、存储和生命周期管理的服务运行，不得导入 QuotaHot 代码、复用 QuotaHot 数据库/凭证目录或依赖 QuotaHot 进程启动。QuotaHot 可通过版本化 HTTP/REST 与 SSE 契约作为可选客户端接入。

### Key Entities *(include if feature involves data)*

- **消息目标**：使用者明确选中的 DingTalk 用户或群，包含目标类别及用于准确路由的身份。
- **事件订阅**：一个消息目标对应的一段监听活动，由独立 DingTalk Inbox 服务拥有，包含目标、运行状态及可用的开始/停止信息。
- **消息**：属于一个明确会话的入站或出站内容，包含身份、发送者、时间、内容和发送/接收状态等可用信息。
- **聊天会话视图**：围绕一个消息目标展示的消息序列；不得把联系人搜索结果或未确认会话当作消息目标。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者在 3 次操作内可从搜索结果打开指定用户或群的聊天视图，且目标身份和类型可被辨认。
- **SC-002**: 在监听已就绪且上游正常的验收中，至少 95% 的测试消息在 5 秒内显示于正确聊天框。
- **SC-003**: 至少 99% 的并行用户/群消息路由测试显示在正确会话中，错误会话展示数为 0。
- **SC-004**: 在至少 20 次发送测试中，100% 的回复目标与发送前界面标识的聊天目标一致；失败或未知结果均未显示为已送达。
- **SC-005**: 5 名代表性使用者中至少 4 名可在无指导下完成搜索目标、启动监听、查看消息及发送文本回复的完整任务。
- **SC-006**: DingTalk 运行时能力不可用的验收场景中，系统错误宣告功能可用或静默切换到联系人/会话/轮询模式的次数为 0。
- **SC-007**: 独立服务在无 QuotaHot 源码、进程、配置及数据目录的环境中可独立构建和启动；重启或停止 QuotaHot 不改变 DWS 订阅或消息持久化状态。

## Assumptions

- 此规格定义独立于现有 WeChat 功能的 DingTalk 消息服务，不改变 `001-wechat-user-list` 中的微信用户绑定及消息行为；它不作为 QuotaHot 内置功能模块实现。
- 第一版范围包括用户和群的关键词搜索、单个当前目标的消息事件监听、文本消息接收展示和文本回复；多目标同时监听、附件、富媒体、历史消息补拉及群管理不纳入本规格。
- 事件只在监听状态明确为就绪后才保证开始接收；是否在 Web 页面关闭或服务重启后持续监听，需根据运行时能力确认并在界面中如实体现。
- 使用者已具备访问该 DingTalk 组织及相应搜索、读取、事件订阅和发送权限。
- **运行时边界**：DingTalk 搜索、事件监听、消息存储和消息发送由独立 DingTalk Inbox 服务负责，并通过受支持的 `dws` CLI 子进程调用；该服务不依赖 QuotaHot 的包、进程、数据库或凭证目录。QuotaHot Web 可作为可选客户端，通过服务 API/SSE 接入；开发代理侧安装的 skill 仅作为能力参考，不是服务运行时。
- **目标语义**：选择用户表示与该用户的一对一单聊；群消息只在使用者明确选择对应群后显示。某用户在其他群里的发言不归入与该用户的单聊。
- **规划门禁**：进入实现前必须证明独立服务部署环境可提供符合本规格的搜索、持续事件消费和发送能力，并验证服务可脱离 QuotaHot 构建、运行和持久化。不能证明时应将功能标为受阻并调整接入方案，不得以联系人或会话模型替代。
