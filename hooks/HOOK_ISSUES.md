# OpenCode Hook 自动切换问题记录

记录日期：2026-09-09。时间线使用 Asia/Singapore（UTC+8）。

## 1. 结论摘要

本次“账户 limit 后没有自动切换”不是单一问题，而是两层故障叠加：

1. 第一次故障中，OpenCode 启动早于新版插件安装，运行中的旧插件不处理重试事件，只在最终错误时尝试切换。
2. 重启后仍失败，是因为候选账户额度查询受到 Headroom 传输包装影响。配置代理时的 Undici 路径尝试 HTTP/2，被 shim 拒绝；直接换成全局 fetch，又遇到 Headroom 的上游地址限制。

本轮已实现并安装 hook 专用 HTTP/1.1 额度查询通道，同时修复 SDK 返回值解包和失败结果提示。保留 Headroom 注入的真实额度查询与隔离凭证切换验证通过。

**验证边界：已验证 retry 事件到双端凭证更新的链路；尚未在用户真实会话中再次制造限额并观察模型恢复。最终错误后的自动续跑也未实现。**

## 2. 必须保留的使用前提

- OpenCode 配置的 OpenAI OAuth 模型与 Codex 共用同一个 ChatGPT 账户 token。
- 自动切换仍应将选中的账户同步给 Codex 和 OpenCode，而不是把两边改成独立账户。
- “hook 与服务代码隔离”不等于“两个客户端的账户隔离”。
- 不需要 QuotaHot Web 服务运行，hook 可以自行读取账户、查询额度和写回认证文件。
- 凭证续期会涉及 refresh token 轮换，不能为了代码隔离而复制一套互不协调的刷新逻辑。

此前用“Codex=A、OpenCode=B”复现出的错归属问题，应定位为共享登录前提被破坏时的异常风险，不是正常共用 token 场景必然发生的错误。

## 4. 已确认原因与证据

### 4.1 插件文件更新不等于运行实例重新加载

OpenCode 插件初始化后保留在运行实例中。更新 `quotahot.js` 后，需要退出并重启 OpenCode 才能可靠加载新版事件处理逻辑；可以继续原会话，不要求一定新建会话。

部署链路必须分别确认：源码、构建产物、本机可执行文件、生成插件、运行实例。只更新其中一项不能证明整条链路已更新。

### 4.2 Headroom 拦截候选额度查询

原路径：

```text
OpenCode 插件
  → quotahot-hook run opencode
  → switchAccount / assess
  → queryUsage（usageTransport: fetch）
  → 服务公共 HTTP 层
  → 配置代理时使用 undici.fetch
  → HTTP/2 连接被 Headroom shim 拒绝
```

只读复现得到：

```text
Headroom OpenCode wrap blocked direct HTTP/2 connection
to https://chatgpt.com.
Use fetch, http, or https so traffic can be routed through Headroom.
```

保持相同查询逻辑和应用代理，只在诊断子进程中移除 shim 注入后：一个账户查询成功且可用，另一个查询成功且已触限。这证明不是没有可用账户，而是查询路径不可用。

进一步直接使用全局 fetch，响应为 HTTP 400：

```text
Rejected unsafe upstream base URL
```

因此，“统一改成 fetch”并不是有效修复。Headroom 还会包装子进程创建并注入 shim，单纯把代码放进子进程也不能自动隔离该影响。

**历史证据限制：当时 hook 子进程的 stderr 未保留，不能声称拿到了该次失败的完整错误报文。传输原因通过后续同环境只读对照复现确认。**

### 4.3 SDK 返回值没有解包

插件补查会话消息时，标准 SDK 返回形态为：

```js
{ data: [...], request, response }
```

原实现只接受直接数组，因此缓存缺失时无法确认 provider，静默跳过切换。原测试 mock 返回直接数组，掩盖了契约问题。

回放结果：直接数组启动子进程 1 次，SDK 包装对象启动 0 次。已修复为正确读取 `.data`，同时保留原有数组输入支持。

### 4.4 未成功结果没有可见反馈

原插件丢弃子进程 stderr，且只提示成功切换；额度查询失败、无候选、运行异常都容易表现为“没有反应”。

本轮增加 `check_failed` 结果，使用固定提示区分检查/写入失败与普通未切换，并在结果变化时记录安全结果代码。连续相同结果去重，不输出 token、邮箱或原始上游响应。日志调用自身异常不会使 hook 拒绝事件。

### 查询策略

- 使用导入的 `undici.fetch`，不调用被包装的全局 fetch。
- 直连 `Agent` 和代理 `ProxyAgent` 显式关闭 HTTP/2，代理目标的 TLS 配置同样关闭 HTTP/2。
- 遵守现有 `proxy` 和 `noProxy` 配置，不修改服务 dispatcher 或全局传输设置。
- 每个候选账户的两个备用查询地址共用 15 秒预算；这不是所有账户的总时限。
- 只查询额度，不查询 profile 或 reset-credit 明细。
- 仅在地址未路由的响应下尝试备用路径；401、429 不作为换地址重试的理由。
- 无有效额度数据、非 JSON、网络错误等结果不当成可用账户。
- 查询完成后释放专用 dispatcher。

### 隔离程度的准确描述

**本轮完成的是查询传输隔离，不是整个 hook 与服务代码完全解耦。**

仍复用账户读取、配置、纯解析函数、凭证锁、切换状态和双客户端写回逻辑。`src/server/http.ts` 与服务公共额度查询实现没有因本次修复而改变。若后续做完全独立构建，必须继续遵守同一套凭证刷新协调协议。

## 8. 仍未完成的事项与已纠正判断

### 8.1 凭证更新与会话恢复是两个验收目标

- OpenAI OAuth 实现会在每次 fetch 中重新读取认证，不能仅凭 SDK 缓存就断言当前会话无法采用新 token。
- retry 阶段还有后续请求，及时换好凭证后可以被后续请求采用。
- `session.error` 是终止路径。当前插件没有自动重新提交或恢复失败轮次的动作。
- 本轮未在用户真实会话中再次制造 limit 并确认模型成功响应，也未验证所有第三方 provider 插件或其他传输方式。

### 8.2 先前审查发现但本轮未修复的风险

以下不应与本次已确认的传输故障混为一谈：

- 最终错误路径仍缺少与 retry 路径一致的 provider 归属检查，其他 provider 的限额事件可能误触发共享账户切换。
- CLI 的限额判定仍会对整个事件字符串匹配，存在无关字段误命中的风险。
- 两个认证文件只有一个写入成功时，现有协调器仍可能报告切换成功，需要区分部分成功。
- 两边登录状态不一致或无法识别当前账户时，归属与恢复策略仍需明确。
- 候选串行查询、全局切换时限、失败账户隔离与额度快照缓存的分离仍待优化。
- 过期凭证的续期路径仍复用原有实现；本次成功链路使用有效 token，不代表 Headroom 环境下的所有续期场景已验证。

### 8.3 不再采用的错误推断

- “两边同时写回就是 bug”：不成立，违背实际共用 token 的前提。
- “子进程不会受到父进程的 Headroom 包装影响”：不成立，shim 会注入子进程。
- “SDK 被缓存，所以改 auth.json 必须新建会话”：证据不足，OpenAI OAuth fetch 有逐请求读取认证的逻辑。
- “所有 error 都会切换”：不准确，CLI 仍有信号检查；问题是缺少 provider 归属约束及信号范围过宽。

## 9. 再次失败时的检查顺序

1. 核对实际可执行文件、插件安装时间、OpenCode 实例启动时间，避免只检查仓库源码。
2. 从日志区分 `session.status: retry` 与最终 `session.error`，记录首次触限、最后一次重试和手动切换时间。
3. 检查安全结果代码：`switched`、`check_failed`、`no_candidate`、`unknown`。注意 `no_candidate` 当前也可能涵盖冷却等未切换情况。
4. 在保留真实 Headroom 和代理环境的前提下，只读验证候选额度；不要直接执行会修改真实认证文件的 hook 来“试一下”。
5. 将“选中候选”“两个文件写入成功”“后续请求采用新凭证”“会话恢复响应”分别验证，不要用前一步替代后一步。
6. 排障输出只保留时间、状态、结果代码与匿名账户编号，不粘贴 access token、refresh token 或完整认证文件。
